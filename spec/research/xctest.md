# xctest: Public XCTest/XCUIAutomation API surface on Xcode 26.6 / iOS 26 for driving another app (TestFlight Hagah, SpringBoard, Control Center, system sheets) on a physical iPhone from a long-lived UI-test runner

## SUMMARY
I checked the local Xcode 26.6 (17F113) iPhoneOS SDK headers. UI automation lives in a standalone XCUIAutomation framework, split out in Xcode 16.3, and XCTest re-exports it. Every XCUI class is @MainActor. The public surface is enough for the core work: XCUIApplication(bundleIdentifier:) with launch/activate/terminate/state/wait(for:timeout:)/open(_:), queries plus firstMatch, waitForExistence/waitForNonExistence/wait(for:toEqual:timeout:), snapshot() with dictionaryRepresentation, XCUIScreen.main.screenshot() (whole screen, any app in front), typeText, and XCUICoordinate tap/press/press-then-drag-with-velocity-and-hold. Absolute screen taps also work through a coordinate taken from the SpringBoard XCUIApplication. Some things have no public API. There is no multi-point or curved touch path, and no coordinate-level swipe on iOS (the XCUICoordinate swipes are marked API_UNAVAILABLE(ios)). There is no lock or side button: XCUIDevice.Button on iOS 26 is home/volumeUp/volumeDown/action/camera, and iPhone 12 only has home and volume. You cannot turn off the pre-/post-event 'wait for app to idle', and you cannot bypass Face ID or the passcode. WebDriverAgent covers these gaps with private APIs: pressLockButton (still works on iOS 26; on iOS 27 it needs an IOHID Power event), XCPointerEventPath/XCSynthesizedEventRecord, quiescence swizzles, and failure-halting overrides. The biggest new finding is a likely blocker. iOS 26.1 ships AutomationModeUI.app, which shows a translucent, moving 'Automation Running / Hold both volume buttons to stop' overlay on physical devices for as long as an XCTest UI session is live. Reports say it is missing from XCTest screenshots, but nobody has checked it against a USB/CoreMediaIO capture (OBS/QuickTime). That has to be spike #1, because it collides with the rule that nothing of the tool may appear in the recording. The second big risk is quiescence. While audio plays, Hagah runs a requestAnimationFrame loop every frame (useKaraokeWord.ts) and writes a Reanimated shared value per frame (VerseTimeline.tsx). XCUIAutomation still logs 'Wait for %@ to idle' and 'App animations complete notification not received, will attempt to continue', so taps during scenes 2-5 may stall. The Control Center airplane toggle is reachable as springboard.switches["airplane-mode-button"] (decompiled iOS 26.1 accessibility bundle, and Patrol HEAD Oct 2026). The Sign in with Apple sheet probably lives in com.apple.AuthKitUIService, but that is unverified on iOS 26 hardware, and OCR plus absolute taps is the fallback. Vision word boxes are well supported: VNRecognizedText.boundingBox(for:) gives word precision at .accurate; RecognizeTextRequest needs iOS 18; RecognizeDocumentsRequest exposes words on iOS 26. A14 latency has to be measured. Test timeouts are off by default (executionTimeAllowance only applies when -test-timeouts-enabled YES), so a single test that spins the main run loop can live for hours, as WebDriverAgent does. But any hard XCUI failure halts that test unless continueAfterFailure and the private halt flags are handled. Device-level prerequisites belong in the setup checklist: Auto-Lock Never, Low Power Mode off (it forces a 30 s Auto-Lock), Enable UI Automation ON, passcode entry about once a day before automation starts, Focus on, runner and host icons moved off the home screen, XCTest automatic screen capture disabled, and no automatic update to iOS 27.

## RISKS
- [blocker] The 'Automation Running / Hold both volume buttons to stop' overlay (AutomationModeUI.app) appears in the OBS/CoreMediaIO USB capture during the take
  why: iOS draws it on physical devices for the whole time an XCTest UI session is live (confirmed present in iOS 26.1 strings). It is translucent and moves around. Reports say it is excluded from XCTest screenshots, but nothing covers USB screen mirroring. This would break the hard rule that nothing of the tool is visible.
  spike: S0.1. Start the runner over USB (xcodebuild test-without-building), let it go idle in the background, open Hagah, record 3 min in OBS (and once in QuickTime) at 100% brightness on light and dark screens. Run ffmpeg frame extraction at 2 fps plus macOS Vision OCR over the frames looking for 'Automation Running' / 'volume buttons', and compare with what the phone screen shows. Repeat (a) after detaching xcodebuild while the runner stays alive, and (b) with an on-device ReplayKit Control Center screen recording.
  success: 0 of about 360 OBS frames contain the overlay text or its glyph, while it is visibly present on the phone, under both configurations.
  planB: (1) If ReplayKit excludes it, record on the device (Control Center Screen Recording) and pull the file. (2) Run per-scene XCTest sessions: start the runner only for each action burst and end it during narration holds, and measure the startup cost. (3) Owner decision: accept it and disclose it, or blur/mask it if its position stays stable within a scene. Mark as ❓ owner decision.

  spike: S0.2. In the Hagah reader with audio playing, run 20x element.tap() on a label query, 20x a springboard-coordinate tap, 20x press(forDuration:thenDragTo:), and 20x snapshot(). Log wall-clock per call and capture the runner's os_log for 'Wait for app.kifactory.hagah to idle' and 'not received'. Repeat with audio paused as a baseline.
  success: p95 tap latency ≤ 1.0 s and p95 snapshot ≤ 1.5 s with audio playing; zero 'failed to quiesce' or 'notification not received' lines; latency within 2x of the paused baseline.
  planB: Private, isolated in one module: wrap events in -[XCUIApplication _performWithInteractionOptions:(SkipPre|SkipPostEventQuiescence) block:], or apply the WDA-style swizzle of -[XCUIApplicationProcess waitForQuiescenceIncludingAnimationsIdle:isPreEvent:] with a 0.5 s cap, or synthesize through XCSynthesizedEventRecord. Choreography plan B: pause audio, act, resume, where the script allows.
- [high] Locking the screen (scene 3) has no public API

## RECOMMENDATIONS
- Treat 'Automation Running' overlay vs. OBS capture (S0.1) as the first phase-0 spike and a gate. Its result decides whether the whole long-lived-runner architecture holds for the take mode.
- In architecture.md, split the runner into PublicCore (XCUIAutomation only) and PrivateShim (one Swift/ObjC module behind protocols, every symbol listed with risk and plan B): pressLockButton / XCDeviceEvent(0x0C,0x30), _performWithInteractionOptions:/quiescence swizzle, XCSynthesizedEventRecord multi-point paths, _XCT_requestScreenshot JPEG, shouldHaltWhenReceivesControl. Each shim needs a runtime respondsToSelector check and a public fallback.
- Run every XCUI call on the main actor: an HTTP/socket server on a background queue, commands dispatched to DispatchQueue.main, and the single test method spinning RunLoop.main (the WDA pattern). Never block main with semaphores.
- Make the long test failure-proof: continueAfterFailure = true, override record(_:) to log, and resolve every target first (snapshot or waitForExistence) so XCUI calls never fail. Have the Mac side restart the runner if the test method exits.
- Locate targets explicitly by label: descendants(matching: .any).matching(NSPredicate(format: "label == %@", …)).firstMatch, with labels taken from packages/core/src/i18n/messages/en. Keep OCR (Vision accurate/word boxes, or iOS 26 RecognizeDocumentsRequest.words) as the fallback for text that is not in the tree. Tap through an absolute springboard coordinate.
- Use one primitive for every tap and drag: XCUICoordinate from the springboard app plus withOffset(points). Express drags as press(forDuration:thenDragTo:withVelocity:thenHoldForDuration:) with explicit velocity (pixels/s) and hold. Document that curved paths are out of scope unless the private path is approved.
- In take mode, never call launch() or app.open(_:) on Hagah. Use home-icon taps (sb.icons["Hagah Bible"]), activate() only for recovery, and XCUIDevice.shared.system.open(hagah://…) only for exploration or resets.
- Record every action with a monotonic timestamp before and after the call, because XCUI actions are synchronous and include variable quiescence and snapshot waits. Schedule choreography steps as 'not before T' rather than fixed sleeps, and report per-step latency.
- Disable XCTest diagnostic capture for the runner: in the test plan set preferredScreenCaptureFormat=screenshots and systemAttachmentLifetime/uiTestingScreenshotsLifetime=keepNever, and in +setUp set UserDefaults DisableDiagnosticScreenRecordings=YES and DisableScreenshots=YES. Pass -test-timeouts-enabled NO.
- Add device-setup checkpoints to the spec: Settings > Developer > Enable UI Automation ON; Auto-Lock Never; Low Power Mode off; Focus/Do Not Disturb on; Auto-Correction, Predictive Text and Smart Punctuation off (if typing a note); runner and host icons removed from the Home Screen (App Library only); automatic iOS updates off; passcode entry when automation starts; cable connected and devicectl transportType wired.
- Model the human checkpoints with public detection only: Face ID or passcode on the SIWA sheet, detected by waitForExistence on Hagah's post-login element or by AuthKitUIService disappearing; unlock after scene 3, detected by the 'com.apple.springboard.lockstate' notify state returning to 0 followed by press(.home); airplane toggle confirmed by the value of switches["airplane-mode-button"].
- Add an explicit rule to the constitution: the runner never presses both volume buttons and never uses the volume buttons in a take, because they show the HUD and holding both ends automation.
- Make sure the runner Xcode project has no target or product with bundle id app.kifactory.hagah, so init(bundleIdentifier:) can never install over the TestFlight build. Add this as an automated check in the build script.
- Capture Xcode 26.4+ crash-log warnings for Hagah from the xcresult as diagnostic output of each take.

## FINDINGS
### F1 [verified] Since Xcode 16.3, UI automation lives in a separate XCUIAutomation framework. XCTest re-exports it, and in Xcode 26.6 the XCUI headers inside XCTest.framework are only forwarding shims.
Release note 137059728: 'The XCTest APIs related to UI automation testing have been moved to a new, standalone framework named XCUIAutomation. XCTest re-exports XCUIAutomation so import XCTest continues to import'. Local check: XCTest.framework/Headers/XCUIApplication.h contains only '#import <XCUIAutomation/XCUIApplication.h> // contents moved'. Framework Info.plist: CFBundleShortVersionString 16.0, DTSDKName iphoneos26.4, DTXcodeBuild 17F109, MinimumOSVersion 13.0. Apple docs list these symbols as 'Xcode 16.3' under /documentation/xcuiautomation. Every class is annotated XCUI_SWIFT_MAIN_ACTOR (@MainActor), so the runner's command server must marshal every XCUI call to the main thread/run loop. Because the frameworks are embedded in the runner, API availability mostly follows the Xcode version, not the iOS version, except where API_AVAILABLE(ios(...)) is stated.
SRC: https://developer.apple.com/documentation/xcode-release-notes/xcode-16_3-release-notes ; /Applications/Xcode.app/Contents/Developer/Platforms/iPhoneOS.platform/Developer/Library/Frameworks/XCUIAutomation.framework/Headers/XCUIAutomationDefines.h (XCUI_SWIFT_MAIN_ACTOR)

### F2 [verified] XCUIApplication app-lifecycle API (Swift names), with exact semantics for a non-test-target app
init(bundleIdentifier: String); func launch() is synchronous and terminates any running instance first, so you get a cold start and splash screen; func activate() is synchronous, does NOT terminate a running app, and launches it if it is not running (reusing the args from the previous launch()); func terminate() halts through the debugger if one is attached, otherwise sends SIGKILL; var state: XCUIApplication.State {get} is passively monitored and asynchronous (.unknown=0, .notRunning=1, .runningBackgroundSuspended=2 [iOS only], .runningBackground=3, .runningForeground=4); func wait(for state: XCUIApplication.State, timeout: TimeInterval) -> Bool (the Swift name of waitForState:timeout:); func open(_ url: URL) iOS 16.4+ 'Launches the application synchronously using the provided URL... similar to -launch' (may relaunch: spike it); launchArguments/launchEnvironment only take effect at the next launch. The header says 'Any failure in the launch sequence will be reported as a test failure and the test will be halted'. Implication for Contrarregra: use activate() or a home-screen icon tap, never launch(), in the middle of a take; launch() is fine for a clean reset during exploration.
SRC: Xcode 26.6 SDK: XCUIAutomation.framework/Headers/XCUIApplication.h ; https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/wait(for:timeout:)

### F3 [verified] init(bundleIdentifier:) can INSTALL a matching build from the test scheme over the installed app
Apple doc: 'XCUIAutomation detects a matching build... Any matching build in the Target Dependencies list... Build action... root level of the test target's Build Products folder. For iOS and tvOS apps, the system installs the matching app build onto the device and launches it. If the system can't find the matching app build, it launches the existing installed app for the requested bundle ID.' Implication: the Contrarregra project/scheme must never contain any target or product with bundle id app.kifactory.hagah, otherwise the untouched TestFlight build gets overwritten. The UI-test target's 'Target Application' should be the minimal host app.
SRC: https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/init(bundleidentifier:)

### F4 [likely] launchArguments/launchEnvironment have no effect on the untouched TestFlight Hagah build
They are just argv/env for the process. Hagah has no code that reads them (no debug hooks by design), so they cannot change its behavior or disable animations. The usual mitigations ('pass -UITests to disable animations') are therefore unavailable. Hagah does register URL scheme 'hagah' (apps/mobile/app.json) and https universal links, so deep links through XCUIDevice.shared.system.open(_:) are a public, hook-free way to navigate during exploration and resets.
SRC: /Users/noah/project/bible/hagah/apps/mobile/app.json (scheme 'hagah', name 'Hagah Bible') ; XCUIApplication.h launchArguments doc

### F5 [verified] XCUIDevice.shared.system.open(_ url: URL) opens a URL in the default app (Xcode 14.3+, iOS 16.4+ runtime)
XCUISystem: func open(_ url: URL), 'Open a URL on the system using the default application for it.' Xcode 14.3 release notes: 'You can now open a URL using a specified application, or tell the device to open a URL using the default application for it (21387710).' WDA reports 'This API requires an iOS 16.4+ runtime'. WWDC25-344 shows XCUIDevice.shared.system.open(customURL) next to app.open(customURL).
SRC: XCUIAutomation.framework/Headers/XCUISystem.h ; https://developer.apple.com/documentation/xcode-release-notes/xcode-14_3-release-notes ; https://developer.apple.com/videos/play/wwdc2025/344/ ; appium/WebDriverAgent@9d1d17d:WebDriverAgentLib/Categories/XCUIDevice+FBHelpers.m:~266

### F6 [verified] Xcode 26.4+ reports crashes of apps driven through XCUIApplication(bundleIdentifier:) as warnings with an attached crash log
Release note 166401942. Useful for diagnosing Hagah crashes mid-take without touching the app.
SRC: https://developer.apple.com/documentation/xcode-release-notes/xcode-26_4-release-notes

### F7 [verified] Query API: type queries, predicates, subscripts and firstMatch
XCUIElementTypeQueryProvider exposes buttons, staticTexts, otherElements, switches, icons, cells, alerts, keyboards, keys, textFields, textViews, webViews, etc., plus `var firstMatch: XCUIElement`, which 'stops the search as soon as a single matching element is found'. XCUIElementQuery offers element, count, element(boundBy:), element(matching: NSPredicate), element(matching:identifier:), subscript[String], allElementsBoundByIndex, allElementsBoundByAccessibilityElement, descendants(matching:), children(matching:), matching(_ predicate:), matching(_:identifier:), matching(identifier:), containing(_ predicate:), containing(_:identifier:). Predicates run against XCUIElementAttributes (identifier, label, title, value, placeholderValue, elementType, isEnabled, isSelected, hasFocus, frame). The header calls subscripting 'a shortcut for matching an identifier only', yet real code matches visible labels with it (e.g. Patrol springboard.alerts.buttons["OK"], the SIWA example buttons["Continue"]). Hagah has 136 accessibilityLabel and 0 testID, so the spec should use explicit NSPredicate(format: "label == %@") or "label BEGINSWITH %@" on descendants(matching: .any).firstMatch.
SRC: XCUIAutomation.framework/Headers/XCUIElementQuery.h, XCUIElementTypeQueryProvider.h ; leancodepl/patrol@4e84f9b:packages/patrol/darwin/patrol/Sources/PatrolImpl/AutomatorServer/Automator/IOSAutomator.swift

### F8 [verified] Waiting API on XCUIElement
func waitForExistence(timeout: TimeInterval) -> Bool (warn_unused_result); func waitForNonExistence(timeout: TimeInterval) -> Bool and func wait<V: Equatable>(for keyPath: KeyPath<XCUIElement, V>, toEqual expectedValue: V, timeout: TimeInterval) -> Bool, both added in Xcode 16 ('A new API on XCUIElement adds the ability to wait for any property... Also, waitForNonExistence has been added' 35419925). Also `var exists: Bool` and `var isHittable: Bool`, documented as 'returns false if the element doesn't exist, is offscreen, or is covered by another element... false for an offscreen element in a scrollable view'.
SRC: XCUIAutomation.framework/Headers/XCUIElement.h + Modules/XCUIAutomation.swiftmodule/arm64-apple-ios.swiftinterface ; https://developer.apple.com/documentation/xcode-release-notes/xcode-16-release-notes ; https://developer.apple.com/documentation/xcuiautomation/xcuielement/ishittable

### F9 [verified] snapshot() returns a full attribute tree: no 'visible' or 'hittable', and debugDescription must not be parsed
func snapshot() throws -> any XCUIElementSnapshot (XCUIElementSnapshotProviding). XCUIElementSnapshot conforms to XCUIElementAttributes (identifier, frame [screen coordinates, points], value: Any?, title, label, elementType, isEnabled, isSelected, hasFocus, placeholderValue, horizontalSizeClass, verticalSizeClass) and adds `children: [XCUIElementSnapshot]` and `dictionaryRepresentation: [XCUIElement.AttributeName: Any]` with keys children, elementType (NSNumber), identifier, value, placeholderValue, title, label, frame (CGRectCreateDictionaryRepresentation), enabled, selected, hasFocus, horizontalSizeClass, verticalSizeClass. Null attributes are omitted. Visibility has to be derived (frame intersected with screen bounds, non-zero area); occlusion is unknown. XCUIElement.debugDescription: 'should be used for debugging only - depending on any of the data as part of a test is unsupported'.
