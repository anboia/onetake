# timing_post: Clock sync, logging, subtitles, guide track, ffmpeg post, simulator rehearsal

## SUMMARY
Use one clock on both sides. On the device, stamp every event with clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW) (= mach_continuous_time = Swift ContinuousClock), which keeps counting through sleep and lock. Also log CLOCK_UPTIME_RAW (= mach_absolute_time, DispatchTime, CACurrentMediaTime), which stops in sleep, so a sleep shows up as a gap between the two. On the Mac, Node 22.19's process.hrtime.bigint() is already mach_continuous_time (libuv 1.51.0), so both ends read the same kind of clock and only offset and skew need estimating. Measure them with NTP-style 4-timestamp exchanges over a dedicated socket, keep the lowest-delay samples, and fit offset(t)=a+b*t from samples taken before, during (best effort) and after the take. Phone clock skews of up to ~87 ppm have been measured, which is ~78 ms over 15 min, so a single pre-take sync does not meet the ±100 ms target. Two error sources are larger than the clock offset: the iPhone->USB->OBS capture latency (unknown, possibly variable) and XCTest quiescence waits before each action (WDA defaults: 10 s idle timeout, 2 s animation cool-off). So the spec should anchor the video timeline after the take by finding visual changes: crop a small region (ROI) around each tapped element and run per-frame signalstats YDIF. On synthetic video this placed the change on the exact frame and beat keyframe noise by ~90x, while whole-frame metrics could not tell a 90x90 px change from a keyframe artifact. OBS chapters are frame-accurate only from OBS 32.0.0. The installed 31.1.2 stamps chapters with the DTS of the last muxed video packet, so they lag by the encoder delay; use them for navigation and as a secondary sync sample, or rewrite them after the take from events.json with an FFMETADATA file. Pin ffmpeg 8.1.1 (/opt/homebrew/opt/ffmpeg/bin): the `ffmpeg` on PATH is 4.4.7, whose ffprobe has no frame pts_time field. Post-production recipes (sentence-level guide track built with adelay/amix/apad, steady ducking with a limited sidechain, two-pass loudnorm to -16 LUFS with -ar 48000, -c:v copy, explicit maps so the chapter data track is not duplicated) were all checked locally with ffmpeg 8.1.1. `say -r` is unreliable on macOS 26.5.2 (Samantha has a rate floor and stays at ~178 measured wpm whatever slower -r is passed; Alex is not installed), so measure real durations and adjust pace with atempo. For the narration booth, run Chrome on http://127.0.0.1: capture PCM with an AudioWorklet and map times with requestVideoFrameCallback plus getOutputTimestamp, and calibrate once with a loopback click. Expected error is about ±20 ms with wired headphones (Bluetooth adds roughly 150-250 ms); the fallback is ffmpeg avfoundation plus a click marker. A TestFlight build cannot run in the Simulator, so rehearsal needs a separate Release simulator build of Hagah from the same commit as the TestFlight build with the store env vars. Airplane mode cannot be rehearsed, and lock, SIWA and Face ID can only be simulated. simctl recordVideo is VFR, probably has no audio, and shares the Mac clock (zero offset), which makes it a good bench for testing the alignment pipeline.

## RISKS
- [high] The iPhone->USB->OBS capture latency L is unknown and may vary: it may grow during static periods because screen-mirror frames are sent only on change, and OBS 'Use Buffering' may smooth them.
  why: L sits directly in the event-to-video error budget (±100 ms) and cannot be removed by clock sync. Old reports cite 'a few 100 ms' and growth while the image is static.
  spike: Calibration run only (never in a take): the host app shows a full-screen CADisplayLink-driven readout of CLOCK_MONOTONIC_RAW ms (big digits plus a binary block code). Record 10 min in OBS at 60 fps, alternating motion with 30 s static periods, with Use Buffering on and then off. Decode the frames on the Mac with Vision OCR or block reads (crop+signalstats). L = frame pts mapped to Mac time (via sync) minus the displayed device time.
  success: median L stable within ±10 ms across the 10 min, and p95-p5 spread ≤ 33 ms (2 frames) in the chosen OBS setting, including the first frame after a ≥30 s static period
  planB: Do not model L. Use per-take visual alignment only: ROI change detection on ≥20 tap events, fit V = alpha + (1+beta)*D, and report residuals. If the spread is still > 100 ms, disable OBS buffering or switch to the QuickTime fallback and re-measure.
- [high] XCTest quiescence/idle waits make the real touch time unknown, possibly by seconds while Hagah animates during playback.
  why: The logged stamp (call start) can precede the real touch by up to waitForIdleTimeout (10 s by WDA default). This breaks both choreography timing and subtitle/event alignment.
  spike: On the device with Hagah playing Psalm 23 (word highlighting active): 50 taps on the mini-player and the Now Playing buttons. Log t_dev_start/t_dev_end per tap, and detect the ROI change in a simultaneous OBS recording. Repeat with quiescence waits disabled or limited (WDA technique).
  success: with waits disabled: p95(t_dev_end - t_dev_start) ≤ 50 ms and p95(|video change - mapped t_dev_end|) ≤ 100 ms
  planB: Use private event synthesis (XCSynthesizedEventRecord, as WDA's W3C actions do) isolated in its own module. Treat video-detected times as authoritative in events.json (t_video_observed) and flag events without a detected change.
- [medium] Clock skew between iPhone and Mac makes a single pre-take offset drift beyond budget over a 15-min take.
  why: Phone skews up to ~87 ppm have been measured (78 ms over 900 s). mach_continuous_time is not disciplined.
  spike: Over USB, run 64-ping bursts every 10 s for 20 min. Fit theta(t) = a + b*t over the min-delay samples, and compute the residual and how far a pre-only and a pre+post fit would extrapolate.
  success: |b| measured; linear-fit residual RMS ≤ 1 ms; pre+post interpolation error at mid-take ≤ 2 ms
  planB: Run periodic mid-take sync bursts on a dedicated socket. If the transport drops (e.g. during airplane mode), bracket with pre+post sync and fall back to the visual-alignment fit, which estimates slope too.
- [medium] USB transport RTT/jitter for sync pings is unknown (usbmuxd forward vs CoreDevice tunnel), and it is affected by large screenshot transfers on the same socket.
  why: Offset error is bounded by delay/2. Head-of-line blocking can push RTT to 100s of ms if sync shares a stream with multi-MB payloads.
  spike: 1000 pings on each transport (usbmux TCP forward; CoreDevice tunnel), first idle and then with concurrent 3 MB screenshot transfers on a second socket. Record min, p50 and p99 RTT, and the std of theta over min-delay samples.
  success: min RTT ≤ 2 ms, p50 ≤ 5 ms, std(theta | lowest 25% delay) ≤ 1 ms, also with concurrent transfers on a separate socket
  planB: Do sync only while idle (pause screenshots), use a dedicated sync connection, or rely on visual alignment for the take and Wi-Fi only for pre/post sync.
- [medium] The installed OBS 31.1.2 places chapters at the last muxed video DTS (encoder-delayed), not at the requested frame.
  why: Chapters will land early by the encoder pipeline delay, so they cannot serve as precise M->V sync samples, and scene chapters may sit visibly before the scene change.
  spike: Record 2 min with 10 CreateRecordChapter calls sent at known hrtime, each paired with an on-screen change caused right after. Compare `ffprobe -show_chapters` times with the visually detected change times and with the request times mapped through GetRecordStatus polling.
  success: chapter bias constant within ±1 frame (16.7 ms) across all 10 chapters, or OBS ≥32.0 shows bias ≤ 1 frame
  planB: Upgrade OBS to 32.2.x (owner decision). Otherwise rewrite the chapters after the take from events.json with an FFMETADATA remux (`-map 0:v:0 -map 0:a -map_chapters 1 -c copy`).
- [medium] Change-detection false positives or negatives on the real take: keyframe artifacts, continuous karaoke highlighting, audio-player progress bars and system animations.
  why: Whole-frame metrics cannot tell small UI changes from keyframe noise (measured 0.31 vs 0.29 YDIF). Continuous animations near the ROI produce constant change.
  spike: On a real OBS take of scenes 2 and 5, run the ROI detector (element frame from the a11y snapshot, scaled pt->px) with YDIF timing plus a tblend YMAX ≥ 64 classifier. Manually verify 30 events frame by frame.
  success: ≥ 90% of tap events detected on the correct frame (±1 frame), with 0 false detections more than 100 ms before the action

## RECOMMENDATIONS
- Clocks (constitution/architecture): the device stamps every event with clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW) (UInt64 ns, == ContinuousClock) and also logs CLOCK_UPTIME_RAW to detect sleep. The Mac uses process.hrtime.bigint() (Node 22.19, libuv 1.51 = mach_continuous_time). Forbid Date() and CLOCK_MONOTONIC for intervals.
- Choreography scheduler: absolute deadlines from the take start, `Task.sleep(until:tolerance:.milliseconds(1), clock: .continuous)` or a DispatchSourceTimer with leeway 0 and .strict. Never rely on the default tolerance (dispatch_after applies a 5-10% leeway). Log the actual wake time and lateness per step.
- Sync protocol: a dedicated socket (not shared with screenshots); 32-ping bursts at 10 ms spacing; keep the lowest-delay 25%; NTP formula (RFC 5905). Take bursts at T-60 s, every ~20 s during the take (best effort), and after stop. Robust linear fit a+b*t; store samples, fit, skew_ppm and residual in events.json. Fail the take's 'sync quality' check if residual > 2 ms or |skew| > 150 ppm.
- Video mapping: make post-hoc visual alignment the primary method. For each tap, crop an ROI (the element frame from the a11y snapshot × 3 px/pt × OBS canvas scale; keep the OBS canvas at native 1170x2532 to make this trivial). Time the change with signalstats YDIF, classify it with a tblend YMAX ≥ 64 check (correcting tblend's +1 frame offset), and use windowed `-copyts -ss -t` before -i. Fit V = alpha + (1+beta)*D_mac. events.json keeps t_dev_start_ns, t_dev_end_ns, t_video_pred_s, t_video_observed_s and detection score per event.
- Define SM 'sync error ≤ ±100 ms' operationally: over ≥ 20 tap events with immediate visual feedback, |t_video_observed - t_video_pred| has median ≤ 50 ms and p95 ≤ 100 ms, computed by the CLI after every take.
- OBS chapters: on 31.1.2 treat them as navigation only (biased by encoder delay). Record the Mac hrtime of each CreateRecordChapter as an extra sync sample. Always regenerate final chapters from events.json via FFMETADATA (`-map 0:v:0 -map 0:a -map_chapters 1 -c copy`). Put an 'upgrade OBS to ≥ 32.0 for frame-accurate chapters' item in Decisões do dono.
- Pin ffmpeg/ffprobe to /opt/homebrew/opt/ffmpeg/bin (8.1.1) in config; check the major version ≥ 7 at startup. The PATH binary is 4.4.7.
- Final export recipe (spec it as-is): adelay for the narration offset (never -itsoffset with filters); a limited-sidechain sidechaincompress for steady ducking (ratio 2-3 for ~8-12 dB); amix normalize=0; two-pass loudnorm I=-16:TP=-1.5:LRA=11 with linear=true; -ar 48000; -c:v copy (or libx264 crf 18 / h264_videotoolbox if OBS did not record H.264 yuv420p); -c:a aac 192k; explicit -map 0:v:0; chapters kept; -movflags +faststart.
- Subtitles: generate both .srt and .vtt from events.json plus the script, timed in final-video time. Each cue has 2 lines: line 1 <i>[Sx · action]</i>, line 2 a sentence or clause of the suggested line (≤ 42-64 chars). Durations come from per-sentence guide synthesis, clamped to 0.83-7 s with a ≥ 2-frame gap. Offer an optional mov_text track in a review copy only, never in the App Review deliverable.
- Guide track: per-sentence `say -v Samantha -o x.wav --file-format=WAVE --data-format=LEI16@48000`. Measure durations with ffprobe and scale by the owner's measured pace (atempo or factor k). Build the timeline with adelay(all=1) + amix(normalize=0) + apad(whole_dur=video). Make the voice configurable (Daniel or Reed respond to -r; Alex is not installed). Gemini TTS is an optional backend reusing Hagah's config, without API calls in the spec phase.

Map times with requestVideoFrameCallback (mediaTime ↔ expectedDisplayTime) and AudioContext.getOutputTimestamp (contextTime ↔ performanceTime). Subtract input latency (Chrome track stats/settings) and one-time loopback calibration, require wired or built-in output, and write voice.wav plus voice_offset_s. Fallback: ffmpeg avfoundation 48k/24-bit plus a click/clap onset (silencedetect). Expected error is about ±20 ms when calibrated.

## FINDINGS
### F1 [verified] On Darwin, CLOCK_UPTIME_RAW == mach_absolute_time and stops while the system sleeps. CLOCK_MONOTONIC_RAW == mach_continuous_time and keeps counting through sleep. CLOCK_MONOTONIC on Darwin is gettimeofday() minus boottime, i.e. derived from the wall clock with microsecond resolution.
Libc clock_gettime_nsec_np: `case CLOCK_MONOTONIC: _mach_boottime_usec(&boottime,&tv) ... return timeval2nsec(tv) - boottime`; `case CLOCK_MONOTONIC_RAW: mach_time = mach_continuous_time()`; `case CLOCK_UPTIME_RAW: mach_time = mach_absolute_time()`. macOS 26.5 man page: CLOCK_MONOTONIC_RAW is 'unaffected by frequency or time adjustments'; CLOCK_UPTIME_RAW 'does not increment while the system is asleep' and is identical to mach_absolute_time() after timebase conversion. Implication: stamp device events with clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW) (UInt64 ns). Do not use CLOCK_MONOTONIC (wall-derived, µs) or Date() for intervals.
SRC: https://github.com/apple-oss-distributions/Libc/blob/63976b830a836a22649b806fe62e8614fe3e5555/gen/clock_gettime.c#L86-L125 (tag Libc-1752.120.2); `man clock_gettime` on macOS 26.5.2

### F2 [verified] Apple documents mach_absolute_time as not incrementing while asleep, and mach_continuous_time as 'like mach_absolute_time, but advances during sleep'.
Apple doc abstract: 'Returns current value of a clock that increments monotonically in tick units (starting at an arbitrary point), this clock does not increment while the system is asleep.' The SDK mach/mach_time.h (Xcode 26.6) declares mach_continuous_time() with that comment, plus mach_continuous_approximate_time(). On Apple Silicon the timebase is 24 MHz (41.67 ns ticks); convert with mach_timebase_info or use clock_gettime_nsec_np.
SRC: https://developer.apple.com/documentation/kernel/1462446-mach_absolute_time ; $(xcrun --show-sdk-path)/usr/include/mach/mach_time.h:53-71

### F3 [verified] On Apple platforms Swift ContinuousClock reads CLOCK_MONOTONIC_RAW (counts through sleep) and SuspendingClock reads CLOCK_UPTIME_RAW (stops in sleep).
swift_get_time: `case swift_clock_id_continuous: ... #elif defined(__APPLE__) clock_gettime(CLOCK_MONOTONIC_RAW, &continuous)`; `case swift_clock_id_suspending: ... clock_gettime(CLOCK_UPTIME_RAW, &suspending)`. Apple docs: ContinuousClock 'does not stop incrementing while the system is asleep'; SuspendingClock 'stops incrementing while the system is asleep'. ContinuousClock.Instant has no public raw value, so serialize with clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW). It is the same clock, so the values are directly comparable.
SRC: https://github.com/swiftlang/swift/blob/2b1908496e5e90b69daf9da78f8928d5e16a07ee/stdlib/public/Concurrency/Clock.cpp#L52-L95 ; https://developer.apple.com/documentation/swift/continuousclock ; https://developer.apple.com/documentation/swift/suspendingclock

### F4 [verified] DispatchTime.now(), DispatchTime.uptimeNanoseconds, ProcessInfo.systemUptime, CACurrentMediaTime and CoreMotion timestamps are all based on mach_absolute_time (uptime, pauses in sleep).
dispatch/time.h (macOS 26.5 SDK): 'On Apple platforms, the default clock is based on mach_absolute_time()'. The only other public base is DISPATCH_WALLTIME_NOW (gettimeofday). An Apple DTS engineer (2026 forum thread) confirms that DispatchTime.uptimeNanoseconds and ProcessInfo.systemUptime derive from mach_absolute_time, and CACurrentMediaTime probably does too. Implication: logging both CLOCK_UPTIME_RAW and CLOCK_MONOTONIC_RAW per event lets you correlate with UIKit/CA timestamps and detect device sleep (the delta between the two grows).
SRC: $(xcrun --show-sdk-path)/usr/include/dispatch/time.h:75-100 ; https://developer.apple.com/forums/thread/847978

### F5 [verified] Task.sleep without an explicit tolerance goes through dispatch_after, which applies a leeway of 5-10% of the delay (minimum 1 ms, maximum 60 s). Sleeping on .continuous sets libdispatch's monotonic (continuous) bit.
Swift DispatchGlobalExecutor.cpp: if tolerance == -1 -> dispatch_after_f(when,...); else a DISPATCH_SOURCE_TYPE_TIMER with the given leeway. clock_and_value_to_time: continuous -> `value | DISPATCH_UP_OR_MONOTONIC_TIME_MASK (1<<63)`. libdispatch _dispatch_after_leeway: '10% leeway for BG and UT, 6.7% leeway for DEF and IN, 5% leeway for UI and above', clamped to [1 ms, 60 s]. Implication: a 20 s scene hold can fire 1-2 s late. The choreography executor should use `try await Task.sleep(until: deadline, tolerance: .milliseconds(1), clock: .continuous)` (or a DispatchSourceTimer with leeway 0 and the .strict flag), compute absolute deadlines from the take start rather than chaining relative sleeps, and log the actual wake time and lateness.
SRC: https://github.com/swiftlang/swift/blob/52d0dc6d49762aac3ef0c7aad8d9eea4854e9326/stdlib/public/Concurrency/DispatchGlobalExecutor.cpp#L205-L345 ; https://github.com/apple-oss-distributions/libdispatch (libdispatch-1542.100.32) src/source.c:1372-1426

### F6 [verified] On the Mac, Node 22.19.0's process.hrtime.bigint() / performance.now() use mach_continuous_time (same clock family as the device ContinuousClock), whereas OBS's internal video clock (os_gettime_ns) uses CLOCK_UPTIME_RAW.
Local `node -p process.versions.uv` gives 1.51.0. libuv v1.51.0 src/unix/darwin.c: `uv__hrtime(...) { return mach_continuous_time() * timebase.numer / timebase.denom; }` (changed in c0a61c3bb3 on 2024-04-15). OBS libobs/util/platform-cocoa.m: `os_gettime_ns(void) { return clock_gettime_nsec_np(CLOCK_UPTIME_RAW); }`. While the Mac stays awake the two run at the same rate with a constant offset. Keep the Mac awake during a take (e.g. `caffeinate -dimsu -w <pid>`).
SRC: https://github.com/libuv/libuv/blob/v1.51.0/src/unix/darwin.c#L60-L63 ; https://github.com/obsproject/obs-studio/blob/3f1a868e05cb7b24b07e38929f1e310c2b970b75/libobs/util/platform-cocoa.m#L41-L44

### F7 [verified] NTP-style offset estimation: theta = 1/2[(T2-T1)+(T3-T4)], delay delta = (T4-T1)-(T3-T2). The offset error is bounded by delta/2, and the most accurate samples are the ones with minimum delay.
T1 = Mac send (hrtime ns), T2 = device receive (CLOCK_MONOTONIC_RAW ns, stamped in the socket read callback before parsing), T3 = device reply send (stamped as late as possible), T4 = Mac receive. Cristian's algorithm is the special case T2 = T3: device_time = T_dev + RTT/2. Suggested protocol: bursts of 32 pings at 10 ms spacing; keep the lowest-delay 25%; take the median theta. Repeat at T-60 s, every ~20 s during the take (best effort) and after stop. Fit theta(t) = a + b*t with a robust fit (Theil-Sen) and store a, b (= skew, ppm) and the residual RMS in events.json. Use a dedicated sync socket, or pause screenshot transfers, so multi-MB payloads do not cause head-of-line blocking. On the device, handle pings on a non-main Network.framework queue, because XCTest calls block the main thread.
SRC: https://www.rfc-editor.org/rfc/rfc5905#section-8 (formulas) and #section-10 (minimum-delay clock filter)

### F8 [unverified] No published RTT figures exist for usbmuxd TCP forwarding or the CoreDevice tunnel over USB. Expected RTT is sub-ms to a few ms (giving offset error of 2.5 ms or less), but this must be measured.
Searches of the libusbmuxd/iproxy, go-ios and WDA docs and issues found no latency benchmarks. For reference, one 60 fps frame is 16.7 ms, so even 5 ms RTT (≤2.5 ms error) is negligible next to frame quantization. Spike: 1000 pings over each candidate transport.
SRC: https://github.com/libimobiledevice/libusbmuxd (iproxy) ; https://github.com/danielpaulus/go-ios (no latency data found)

### F9 [likely] Clock skew between independent devices can reach tens of ppm. A 2013 study measured smartphone skews from -3.17 to +87.43 ppm, so a single pre-take sync is not enough over a 15-minute take.
Cristea & Groza (IEEE Comm. Letters 2013), table 'Clock skew for the phones used in experiment': 22.68, 87.43, -3.17, 20.83 and 16.26 ppm (Android, ICMP timestamps). Worst case 87 ppm x 900 s = 78 ms, which nearly uses up the ±100 ms budget on its own; 20 ppm gives 18 ms. mach_continuous_time is not NTP-disciplined (CLOCK_MONOTONIC_RAW is 'unaffected by frequency adjustments'), so free-running skew applies. Use at least pre+post sync with a linear fit, preferably also periodic mid-take samples. If the post-take sync fails, fall back to the visual alignment fit, which estimates slope as well.
SRC: https://www.aut.upt.ro/~marius-simion.cristea/pdf/phones.pdf (Table I)

### F10 [verified] OBS >= 32.0.0 places chapters frame-accurately: the chapter timestamp is the current render-frame time (obs_get_video_frame_time) at request time, written at the first primary video packet whose composition time is at or after it, using that packet's PTS.
mp4-output.c mp4_add_chapter_proc: `chap.ts = obs_get_video_frame_time()`. The packet callback writes queued chapters when `chap->ts <= pkt_time->cts`, with `chap_dts_usec = (pkt->pts*1000000/pkt->timebase_den) - out->start_time`. mp4-mux.c adds a 'Start' chapter at PTS 0 if the first chapter is later than 0. ### F18 [verified] WebVTT and SRT essentials, and a two-line cue layout.
