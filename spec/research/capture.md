# capture: Capturing a physical iPhone 12 (iOS 26.3) screen and audio over USB on macOS 26.5 (CoreMediaIO/AVFoundation) and recording it with OBS 31.1.2 (Hybrid MP4, chapters, obs-websocket 5.6.2)

## SUMMARY
The iPhone's USB screen stream reaches macOS as a CoreMediaIO device. It shows up in AVFoundation as a single muxed (audio + video) device of type AVCaptureDeviceTypeExternal (ExternalUnknown is the deprecated alias before macOS 14). A process only sees it after it sets kCMIOHardwarePropertyAllowScreenCaptureDevices=1 on kCMIOObjectSystemObject. Apple's WWDC 2014 #508 says this opt-in is required, and OBS, idb and Aperture all set it, even though the macOS 26.5 SDK header still says the default is 1. The property applies per process, and the device appears asynchronously some seconds after it is set. idb polls for up to 10 s; auto-mobile warns that toggling it can stall discovery for up to 60 s. FFmpeg never sets the property, at HEAD or in the local Homebrew ffmpeg@4 4.4.7, and has no flag for it. Even with the opt-in, ffmpeg would take only video from a muxed device, because its audio list comes from microphone-type discovery. So ffmpeg is out unless something else does the opt-in inside its process (plan C). OBS 31.1.2 does the opt-in twice: once at module load in mac-avcapture-legacy, and again when each modern "Video Capture Device" (macos-avcapture) is created. It lists muxed devices, captures the iPhone's audio through AVCaptureAudioDataOutput (no separate audio source needed), and takes the frame size from each sample buffer. The modern source has a confirmed race, OBS issue #12062, still open and still in the code at HEAD: if the iPhone is not present when the source initialises, the later connect notification is ignored. Contrarregra must check that the source is live and re-send SetInputSettings to recover. The device delivers roughly native resolution (1170x2532 for an iPhone 12) at up to 60 fps, variable frame rate (frames are dropped, and none arrive while the screen is static), with 48 kHz LPCM audio. Capture latency is not documented; protocol hints suggest roughly 40-75 ms plus decode, which needs a spike. While capture is active, iOS puts a clean status bar (9:41, full bars and battery, no carrier) on the device itself. This is confirmed up to iOS 17.1 on an iPhone 12 Pro but not yet on iOS 26. It means the airplane-mode icon will almost certainly not appear in the status bar during scene 9, so the proof has to come from Control Center or in-app UI. Hybrid MP4 in 31.1.2 is still labelled [BETA]. It supports CreateRecordChapter (obs-websocket 5.5.0+; 31.1.2 bundles 5.6.2) and multiple audio tracks, and it finalises in place. Chapters are written only at finalisation, and in 31.1.2 each chapter is timestamped at the last muxed packet, so it lands slightly early; 32.0+ makes chapters frame-accurate and 32.2 fixes a crash when a macOS device reconnects. With Apple VT H.264 at 1170x2532 and 60 fps, ABR 16 Mbps comes to about 120 MB/min, or about 1.2 GB for 10 minutes. The 8.7 GiB free is enough for one take, but OBS only stops on its own below 50 MB, so Contrarregra needs its own preflight check and abort threshold. QuickTime Player is fully scriptable (new movie recording / current camera / start / stop / export) and makes a reasonable plan B, with chapters added afterwards by ffmpeg. A Swift helper (CMIO opt-in + AVCaptureSession + AVAssetWriter, as idb does) is plan C.

## RISKS
- [high] The clean status bar hides the airplane-mode icon (and Focus/battery state) in scene 9, so App Review may not see that the device is offline.
  why: iOS swaps in a 9:41 / full-signal status bar on the device during wired capture. This is confirmed through iOS 17.1 and not yet checked on iOS 26.3.
  spike: With OBS capturing, toggle airplane mode from Control Center, return to Hagah and open the downloaded chapter. Record 30 s and inspect frames: (a) status bar contents, (b) whether Control Center shows the Airplane toggle highlighted and real status icons, (c) the in-app 'unavailable offline' message.
  success: At least one of these is clearly visible for 1.5 s or more in the recording: the Airplane toggle on in Control Center, or the in-app offline indicator. Status-bar behaviour on iOS 26.3 is recorded (9:41: yes/no).
  planB: Choreograph scene 9 to hold Control Center open for 2 s with the Airplane tile visible, add a Settings › Airplane Mode shot if needed, or add an on-screen caption in post. Do not rely on the status bar.
- [high] The OBS source does not come up after OBS starts or the cable is replugged (issue #12062 race), or it shows black.
  why: The modern macos-avcapture source ignores late device-connected events when the device was absent at init (deviceUUID nil); the code is unchanged up to HEAD.
  spike: Run 5 cycles each of starting OBS with the cable plugged in, plugging the cable after OBS starts, and replugging mid-session. Each time poll GetSceneItemTransform.sourceWidth and GetSourceScreenshot (64x128 png) for 15 s; if not live, send SetInputSettings {device: UDID} and re-check.
  success: Live within 15 s after a kick, with sourceWidth=1170 and sourceHeight=2532 and a non-black screenshot, in 15/15 trials. Record time-to-appear (target median ≤5 s).
  planB: Kick with device '' then the UDID; create the source fresh via CreateInput (inputKind 'macos-avcapture'); try 'macos-avcapture-fast' (Capture Card Device); upgrade to OBS 32.2.x; fall back to QuickTime (plan B).
- [medium] The capture is not native 1170x2532: the 'High' preset scales or letterboxes, format mode fails because the format reports 0x0 with no frame-rate ranges, or the colours look washed out.
  why: iOS devices expose one 0x0 format; issue #3923 reports the High preset failing on Apple Silicon (2021); a 2024 forum post reports a 'color wash' when capturing iOS in OBS.
  spike: Try four configs: (1) preset High, (2) use_preset=false with the single listed format and 60 fps, (3) Capture Card Device, (4) preset 3840x2160. Check the OBS log line 'Capturing ... Using Format', the source size, and a GetSourceScreenshot at full size compared against an on-device screenshot (pixel diff over a white/grey region).
  success: At least one config gives 1170x2532 with mean RGB difference of 3 or less (0-255) on flat white/grey areas compared with the device screenshot.
  planB: Use the best config with crop and scale-to-inner bounds; fix range or colour with the source's Video range / Color space or a color-correction filter; plan C Swift helper writing native buffers.
- [medium] The iPhone's audio is missing, too quiet, out of sync, or app playback pauses on an audio route change.
  why: Muxed audio routing to the Mac is inferred, not documented. The VFR video and the 48 kHz audio clocks come from the device. Toggling the source can trigger AVAudioSession route changes in expo-audio.
  spike: During capture, play Psalm 23 in Hagah. Check the OBS mixer peaks, whether the phone speaker is silent, and A/V offset measured on play/pause taps and word highlights over 10 events. Hide and show the source once during playback.
  success: Peaks between -20 and -3 dBFS, A/V offset within -45..+45 ms (median), and playback not interrupted by the source hide/show.
  planB: Apply SetInputAudioSyncOffset with the measured offset; never deactivate the source during a take; record narration on a second track; QuickTime (plan B) for audio.
- [medium] Disk runs out mid-take or across retakes (8.7 GiB free), losing chapters or the take.
  why: OBS auto-stops only below 50 MB; chapters are written only at finalisation; retakes and Xcode DerivedData/iOS DeviceSupport also use space; macOS needs headroom for swap with 16 GB RAM.
  spike: Measure free space before and after building and running the XCUITest runner once (DerivedData plus ~/Library/Developer/Xcode/iOS DeviceSupport growth). Then record a 10 min test take at the chosen settings and compare the file size with the estimate. Simulate the abort by setting the threshold above current free space.
  success: Actual size within ±25% of the estimate (≈1.2 GB per 10 min at ABR 16 Mbps / 60 fps). The forced abort produces a finalised MP4 whose ffprobe -show_chapters lists all chapters created so far.
  planB: Drop to 30 fps / ABR 10 Mbps; record to an external SSD (SetRecordDirectory); auto-move or purge failed takes only with user consent; refuse to start below the preflight threshold.
- [medium] Apple VT H.264 hardware cannot encode 1170x2532 at 60 fps on the M4, or falls back or drops frames.
  why: The 2532 px height is unusual (Level 5.1); no primary source was found on dimension limits for the AVE H.264 encoder.
  spike: Start a 2-minute recording at 1170x2532@60 with com.apple.videotoolbox.videoencoder.ave.avc in ABR 16000 kbps. Check the OBS log for encoder creation and hardware acceleration, GetStats output/render skipped frames, and ffprobe (profile high, level, r_frame_rate 60/1).
  success: Encoder initialises in hardware, outputSkippedFrames = 0, renderSkippedFrames < 0.1%, and ffprobe shows 1170x2532 at 60 fps.
  planB: Use Apple VT HEVC (com.apple.videotoolbox.videoencoder.ave.hevc) in Hybrid MP4, or scale the output to 1080x2338 / 886x1920 while keeping the canvas native.
- [medium] Scene 3 (lock with the side button, show lock-screen media controls, unlock) breaks or blanks the capture.
  why: Some mirroring tools show black on the passcode lock screen; a display sleep pauses mirroring; a USB re-handshake could trigger device disconnected/connected events.
  spike: While recording, lock the iPhone, wait 5 s, wake it (lock-screen controls visible), and unlock with Face ID. Watch for AVCapture disconnect logs, black frames, and whether audio keeps playing.
  success: No disconnect event; lock-screen media controls visible in the recording; black only while the display is actually off; capture resumes within 1 s of wake without a kick.
  planB: Change the scene so the screen does not sleep (a short lock then immediate wake); keep a kick routine ready; if the lock screen is black in capture, record that segment with an on-device recording or replace it with a caption or cut.
- [medium] Airplane mode, or the runner's own transport changes, disturb the USB capture stream.
  why: Capture uses the hidden USB configuration and should be independent of radios, but this has not been confirmed on iOS 26.3 with an XCUITest runner also using USB.
  spike: During recording, toggle airplane mode on and off 3 times. Log AVCaptureDeviceWasDisconnected events in OBS and the maximum gap between video frames (via the OBS log or by analysing a recording of a ticking timer).
  success: Zero disconnects and no gap over 500 ms beyond normal static-screen VFR.
  planB: If the stream drops, apply the kick routine automatically and record scene 9 as its own chapter or take.
- [medium] Human checkpoints involving passcode or password entry show black or hidden areas, and notifications appear during takes.
  why: iOS blocks streaming of secure fields and the keyboard; no evidence that wired capture suppresses notifications; the clean status bar hides the Focus icon.
  spike: During capture, type in a secure field and observe the recording. With Focus/DND on, send a notification from another device.
  success: Behaviour documented; with DND on, no banner appears in the recording.
  planB: Do secure-entry checkpoints between takes or between chapters and cut them; add a mandatory pre-flight Focus checkpoint confirmed by a human (or by the runner reading the Control Center Focus tile before recording).
- [low] Chapter markers in OBS 31.1.2 are offset from the scene's first visible frame.
  why: 31.1.2 timestamps chapters at the last muxed packet DTS (lags real time by the encoder/interleave delay); device-to-Mac capture latency adds to this.
  spike: For 10 scene starts, compare the chapter time from ffprobe -show_chapters with the first frame of the scene's visual change, and with GetRecordStatus.outputDuration logged when the chapter was requested.
  success: |offset| ≤ 300 ms (median) and ≤ 500 ms (max) on 31.1.2; ≤ 1 frame on 32.x.
  planB: Rewrite chapters after the take with ffmpeg from the sidecar JSON plus the measured offset (`ffmpeg -i take.mp4 -i chapters.ffmeta -map 0 -map_metadata 1 -map_chapters 1 -c copy out.mp4`), or upgrade OBS to 32.2.x.
- [low] Capture latency is longer than assumed, if any logic relies on the Mac seeing the screen quickly.
  why: No measured glass-to-OBS figure exists; host hints suggest 40-75 ms on the device plus decode and render; old OBS reports describe delays that grow on static screens with buffering enabled.
  spike: The runner logs a device timestamp at a tap that causes a large colour change. The Mac polls GetSourceScreenshot at about 30 Hz and logs the first changed frame. Correct for the clock offset with a ping exchange over the USB control channel. Run 20 trials, with 'Use Buffering' off and on.
  success: Median ≤ 150 ms and p95 ≤ 300 ms with buffering off. The design must not depend on this, since timing is authoritative on the device.
  planB: Keep all choreography timing and checkpoint detection on the device (already decided); use the Mac stream only for recording and optional Mac-side OCR.
- [medium] TCC permissions (Camera/Microphone for OBS; Automation for QuickTime scripting; Camera for a Swift helper launched from a CLI) block the first automated run.
  why: AVFoundation external devices need camera permission; Rotato's support page says mirroring failures are 'most likely related to macOS permissions'; CLI tools inherit TCC from their responsible app.
  spike: On a clean run, check System Settings › Privacy & Security › Camera / Microphone / Automation for OBS, Terminal or Claude, and osascript; trigger each path once.
  success: All three paths (OBS capture, QuickTime AppleScript, helper) run with no pending prompts.
  planB: Make permission grants an explicit one-time human setup step in `contrarregra doctor`, with a precise checklist.
- [low] QuickTime, or another app holding the iPhone capture device, conflicts with OBS (black source).
  why: Forum reports of black iOS sources; a single device-side screen stream is likely exclusive.
  spike: With OBS capturing, open QuickTime New Movie Recording on the iPhone, then close it; observe both apps.
  success: Behaviour documented; the OBS source recovers within 5 s of QuickTime closing (with a kick if needed).
  planB: Preflight checks `pgrep -x 'QuickTime Player'` and refuses to start or asks for it to be quit; never run plan B and OBS together.

## RECOMMENDATIONS
- Capture path: OBS 'Video Capture Device' (inputKind 'macos-avcapture') bound to the iPhone by AVCaptureDevice.uniqueID (expected to equal the devicectl UDID; resolve it with GetInputPropertiesListPropertyItems(propertyName 'device') by matching itemName 'VIVO_00G7'). Start with use_preset=true / AVCaptureSessionPresetHigh and buffering=false, and keep 'macos-avcapture-fast' as the alternative. The resolution spike decides which config ships.
- Implement a source health check plus a 'kick' in the Mac CLI/MCP: after OBS connects, after the cable is plugged, and before StartRecord, require sourceWidth=1170 and sourceHeight=2532 (GetSceneItemTransform) and a non-black GetSourceScreenshot. If either fails, re-send SetInputSettings {device: UDID} (device '' then the UDID if needed) and wait up to 15 s. This works around OBS #12062.
- OBS canvas: Base = Output = 1170x2532, 60 fps (FPSCommon 60; 30 is acceptable), Audio SampleRate 48000. Set the scene item to OBS_BOUNDS_SCALE_INNER at 1170x2532 at position 0,0 so a size change cannot break framing. Set it via SetVideoSettings and SetSceneItemTransform only while no output is active.
- Recording: Output Mode Advanced › Recording › Type Standard, Recording Format 'Hybrid MP4 [BETA] (.mp4)' (AdvOut/RecFormat2=hybrid_mp4), Encoder 'Apple VT H264 Hardware Encoder' (com.apple.videotoolbox.videoencoder.ave.avc). recordEncoder.json: rate_control ABR, bitrate 16000 (60 fps) or 10000 (30 fps), keyint_sec 1, profile high, bframes true. If quality matters more than predictable size, use CRF quality 60-65 with limit_bitrate=true and max_bitrate 30000. Audio Track 1 = iPhone (and Track 2 = Mac narration mic if used) via RecTracks bitmask and SetInputAudioTracks.
- Chapters: call CreateRecordChapter {chapterName: '<NN> <scene title>'} at each scene start, with the first one right after RecordStateChanged OBS_WEBSOCKET_OUTPUT_STARTED to avoid a stray 'Start' chapter. Also append {scene, requestedAt, outputDuration from GetRecordStatus} to a sidecar JSON so chapters can be rebuilt with ffmpeg ffmetadata after a crash, for 31.1.2 offset correction, or for the QuickTime plan B.
- Disk policy: preflight refuses to start unless free ≥ (cap_bitrate × planned_duration × 1.25) + 3 GiB, i.e. at least about 4.5 GiB for a 10 min take at 16 Mbps. During the take, poll GetStats.availableDiskSpace (MiB) every 5 s and issue StopRecord when it falls below 2048 MiB, so Hybrid MP4 still finalises and writes chapters. Report free space in each status reply. Never rely on OBS's 50 MB auto-stop.
- Scene 9 script change: the status bar will read 9:41 with full signal, so prove airplane mode by holding Control Center open with the Airplane tile visibly on for about 2 s, then showing Hagah's offline behaviour. Mention this in the roteiro and the App Review note.
- Human pre-flight checklist (Contrarregra doctor): USB cable plugged in with the iPhone unlocked; approve the Mac 'Allow accessory' and iPhone trust prompts; Focus/DND on; Auto-Lock Never; QuickTime not running; OBS and the terminal or Claude app granted Camera/Microphone (and Automation for plan B); `caffeinate -dimsu` for the take; lid open; no user switching (CMIO suspends devices on a fast user switch).
- Keep the OBS capture source active for the whole session; never hide or deactivate it mid-take, to avoid audio route changes on the iPhone. Leave 'Use Buffering' off unless the A/V sync spike says otherwise, and apply any measured audio offset with SetInputAudioSyncOffset.
- Suggest upgrading OBS to 32.2.x (frame-accurate chapters, macOS device-reconnect crash fix, Hybrid out of beta), but design for 31.1.2 / obs-websocket 5.6.2. Avoid Hybrid MOV/ProRes: about 3 GB/min at this resolution.
- Plan B (QuickTime) automation via osascript: tell application "QuickTime Player" to set r to new movie recording; set current camera of r to (first video recording device whose name is "VIVO_00G7"); set current microphone of r to (first audio recording device whose name is "VIVO_00G7"); start r … stop r; then save or export the resulting document to a fixed path. Add chapters afterwards with ffmpeg from the sidecar JSON (`-map_chapters`); ffmpeg 4.4.7 is enough for this remux.
- Plan C (only if OBS and QuickTime both fail): a small signed Swift CLI modelled on facebook/idb DeviceVideo.swift. Set the CMIO opt-in once (never toggle it); wait for AVCaptureDevice(uniqueID: UDID) up to 15 s or for AVCaptureDeviceWasConnectedNotification; AVCaptureSession with AVCaptureVideoDataOutput (420v) and AVCaptureAudioDataOutput feeding an AVAssetWriter (H.264/HEVC + AAC); chapters added afterwards with ffmpeg. Do not build on ffmpeg's avfoundation input: it has no opt-in and drops the muxed audio.
- Optional architecture note: GetSourceScreenshot on the iPhone source returns full-resolution frames on the Mac, which could feed Mac-side Vision OCR or an 'is the expected screen showing' check without adding anything to the device or the recording.

## FINDINGS
### F1 [verified] A macOS process only sees iOS screen-capture devices after it sets kCMIOHardwarePropertyAllowScreenCaptureDevices ('yes ') to UInt32 1 on kCMIOObjectSystemObject (scope Global, element Main). The macOS 26.5 SDK header says the default is 1, which contradicts what Apple says and what every client does.
Apple WWDC 2014 #508: 'You need to opt in to get this behavior to see iOS devices as AVCapture devices... a single property call on the CoreMedia IO system object telling it to allow screen capture devices.' MacOSX26.5.sdk CMIOHardwareSystem.h (lines 103-106) describes it as 'presented to the process', i.e. per process, and gives 'By default, this property is 1'; the same wording has been there since the 10.15 SDK. OBS, idb, Aperture and auto-mobile all set it explicitly. A sibling property, kCMIOHardwarePropertyAllowWirelessScreenCaptureDevices ('wscd'), defaults to 0; do not use it, since airplane mode kills Wi-Fi anyway. Implication: any Contrarregra process that touches AVFoundation must do the opt-in itself; OBS's opt-in does not carry over to other processes.
SRC: https://nonstrict.eu/wwdcindex/wwdc2014/508/ ; Xcode 26.6 MacOSX26.5.sdk/System/Library/Frameworks/CoreMediaIO.framework/Headers/CMIOHardwareSystem.h:103-123 ; https://developer.apple.com/forums/thread/759245

### F2 [likely] Once opted in, the iPhone appears as an AVCaptureDevice with media type AVMediaTypeMuxed and device type AVCaptureDeviceTypeExternal (macOS 14+; AVCaptureDeviceTypeExternalUnknown is the deprecated synonym, macOS 10.15-14). Its uniqueID is the device UDID.
AVCaptureDevice.h in the 26.5 SDK: ExternalUnknown is API_DEPRECATED_WITH_REPLACEMENT('AVCaptureDeviceTypeExternal', macos(10.15, 14.0)). Discovery: AVCaptureDevice.DiscoverySession(deviceTypes:[.external], mediaType:.muxed, position:.unspecified), as auto-mobile does. facebook/idb finds the device with AVCaptureDevice(uniqueID: device.udid), so uniqueID == UDID, and localizedName == the iPhone's name. Contrarregra can map the devicectl UDID to the OBS 'device' setting directly.

### F3 [likely] The device appears asynchronously after the opt-in, typically within a few seconds. Clients poll or listen for AVCaptureDeviceWasConnectedNotification.
The Apple forum answer says 'It takes a moment for the devices to show up after executing the code'. idb polls AVCaptureDevice(uniqueID:) every 100 ms for up to ControlCoreGlobalConfiguration.fastTimeout = 10 s. auto-mobile's CMIOSystem.swift: 'rapidly toggling this property can stall device discovery for up to 60 seconds, so we only flip it to true and leave it'. OBS registers for AVCaptureDeviceWasConnectedNotification and AVCaptureDeviceWasDisconnectedNotification. Implication: set the property once per process, never toggle it, and wait up to 10-15 s with an event or poll.

### F4 [verified] FFmpeg's avfoundation input never sets the CMIO opt-in and has no option for it, so `ffmpeg -f avfoundation -list_devices true -i ""` will not list the iPhone. The locally installed ffmpeg is Homebrew ffmpeg@4 4.4.7.
A grep for CoreMediaIO, kCMIO and AllowScreen in libavdevice/avfoundation.m at FFmpeg HEAD 98e92563 (file last changed d65fd558, 2026-08-30) finds nothing. getDevicesWithMediaType(AVMediaTypeMuxed) uses AVCaptureDeviceTypeExternal (or ExternalUnknown) at lines 849-866, so muxed devices would be listed if they were visible. The AVOptions (lines 1545-1560) are list_devices, video/audio_device_index, video/audio_device_id, pixel_format, framerate, video_size, capture_cursor, capture_mouse_clicks, capture_raw_data and drop_late_frames; there is no CMIO flag. release/4.4, which is what /opt/homebrew/bin/ffmpeg -> Cellar/ffmpeg@4/4.4.7 runs, uses the deprecated [AVCaptureDevice devicesWithMediaType:AVMediaTypeMuxed] (lines 765-766) and also has no opt-in. Because the property is per process, OBS or a helper setting it does not help an ffmpeg process.

### F5 [likely] Even with the opt-in, ffmpeg would capture only the iPhone's video, not its muxed audio.
The audio device is resolved only from getDevicesWithMediaType(AVMediaTypeAudio), i.e. a microphone discovery session. A muxed device is added only through add_video_device, which attaches an AVCaptureVideoDataOutput (avf_read_header around lines 1255-1312). iPhone audio would need a separate path. This makes ffmpeg a weak plan C even with a DYLD_INSERT_LIBRARIES constructor that does the opt-in.

### F7 [verified] The OBS device list includes muxed devices (the iPhone), and the source captures the iPhone's audio through the same device, so no separate audio source is needed.
plugin-properties.m builds two DiscoverySessions (Video and Muxed) with deviceTypes [WideAngle, ExternalUnknown, DeskView]. createSession adds an AVCaptureAudioDataOutput (lines 137-187). switchCaptureDevice sets obs_source_set_audio_active when the device hasMediaType Audio or Muxed (line 226). Audio samples reach obs_source_output_audio (around line 1466). The iPhone therefore shows up as an audio channel named after the source in the mixer; route it to a track with SetInputAudioTracks. The device audio format is LPCM 48 kHz stereo (per the QVH AFMT packet), so set OBS Audio SampleRate=48000.

### F8 [verified] OBS bug #12062 (open since 2025-04, OBS 31.0.3) is still in the 31.1.2 and HEAD code: if the iPhone is not present when the modern source initialises, the source stays dead even after the device appears.
switchCaptureDevice: when [AVCaptureDevice deviceWithUniqueID:uuid] returns nil for a non-empty uuid, it logs 'Unable to initialize device with unique ID' and returns NO without setting self.deviceUUID (lines 207-215). deviceConnected: compares the new device's uniqueID with self.deviceUUID, which is nil, so it only refreshes properties (lines 1134-1137). updateSession switches when deviceUUID != new UUID (line ~600), so re-sending the settings recovers. Implication for Contrarregra: after OBS start or a cable replug, check the source is live (GetSceneItemTransform sourceWidth>0 or GetSourceScreenshot not black) and if not, 'kick' it with SetInputSettings {device: UDID}, possibly device '' and then the UDID. Separately, OBS 32.2.0 fixed 'potential crash when a video device reconnects on macOS' (commit cc0fd86c05).

### F9 [verified] The OBS source size follows the actual sample-buffer dimensions, and frames carry the device PTS. iOS devices historically expose a single AVCaptureDeviceFormat reported as 0x0, so the OBS maintainer calls the preset 'the canonical way'. The modern defaults are use_preset=true, preset=AVCaptureSessionPresetHigh, buffering=false.

### F20 [likely] Estimated file sizes for a 1170x2532 portrait recording: about 120 MB/min at 60 fps with ABR 16 Mbps, about 77 MB/min at 30 fps with ABR 10 Mbps. Uncapped CRF (Simple 'Indistinguishable') is unbounded, and ProRes is not feasible.
