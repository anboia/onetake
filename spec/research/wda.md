# wda: WebDriverAgent internals (appium/WebDriverAgent v16.13.6 @9d1d17d): runner lifetime, HTTP server, AX snapshots, quiescence, touch synthesis, system ops, private APIs, licence, build-vs-reuse verdict for Contrarregra

## SUMMARY
WDA (latest v16.13.6, released 2026-09-30) stays alive with one test method, UITestingUITests.testRunner. It never returns: it starts the HTTP server and spins the main NSRunLoop until /wda/shutdown. A failure-proof base class swallows every XCTest issue, and a swizzle makes XCTIssue.shouldInterruptTest return NO. XCTest test timeouts are off unless xcodebuild gets -test-timeouts-enabled YES, so the runner dies only when the xcodebuild/testmanagerd session dies, a private call crashes, jetsam kills it, or a human holds both volume buttons on the iOS 15+ "Automation Running" overlay. Since v16.7.0 the server is WDA's own HTTP/1.1 on Network.framework (no longer RoutingHTTPServer/CocoaHTTPServer). By default it listens on 8100 (MJPEG on 9100) on all network interfaces, with no authentication and with CORS set to "*". Every non-"standalone" route runs one at a time on the main queue, so a single hung AX call can freeze the whole agent; issue #1210 shows this on iOS 26.6. Snapshots use the public -[XCUIElement snapshotWithError:] for the application root. Private XCAXClient_iOS parameters (maxDepth 50) are injected by swizzling, and "visible"/"accessible" are private AX attributes (XC_kAXXCAttributeIsVisible/IsElement) fetched lazily from XCTest symbols. Quiescence is disabled by swizzling XCUIApplicationProcess waitForQuiescenceIncludingAnimationsIdle:(isPreEvent:). I disassembled Xcode 26.6's iOS XCUIAutomation locally: there the 1-arg variant is gone, and the 2-arg one is the choke point for every element event, launch and activate. That binary also has a non-swizzle path: -[XCUIApplication _performWithInteractionOptions:block:] with SkipPre/PostEventQuiescence bits. Caveat: after W3C actions and drags, WDA forces up to 2 s of quiescence waiting (animationCoolOffTimeout), which a continuously animating app would always hit. Arbitrary-path gestures and precisely timed taps exist only through the private XCSynthesizedEventRecord/XCPointerEventPath sent via XCUIDevice.eventSynthesizer; that path does not wait for quiescence. Locking the screen exists only privately (pressLockButton, i.e. IOHID consumer page 0x0C usage 0x30). There is no unlock API, and passcode/Face ID stay human. Xcode 26 split XCTest into XCUIAutomation, XCTestCore and XCTAutomationSupport, which forced a full private-header refresh (#1202), and iOS 27 already broke locking and typing. For Contrarregra: copy the techniques, write a small Swift runner, and keep WDA as a debugging fallback. Treat two things as blocker spikes: the iOS 15+ Automation Running overlay and passcode-on-session-start behaviour, and whether people can still touch the phone while automation runs.

## RECOMMENDATIONS
- COPY (technique): use one never-returning XCTest method (testRunner) that spins NSRunLoop.main until a shutdown flag is set, and run all XCTest calls on the main thread. Put a failure-proof base class on top: continueAfterFailure=true, override record(_ issue:) to log only, and swizzle XCTIssue.shouldInterruptTest to NO only if a probe shows it is needed. Do not enable test timeouts; launch with `xcodebuild test-without-building -xctestrun … -collect-test-diagnostics never`.
- COPY: in +setUp, set NSUserDefaults DisableScreenshots=YES and DisableDiagnosticScreenRecordings=YES, and replace XCUIApplication.doesNotHandleUIInterruptions with YES so XCTest never auto-taps alerts or records the screen during a take.
- COPY: model WDA's 'standalone' routes. Keep a control lane (health, abort, status, take progress) on its own queue that never waits on XCTest, and an XCTest lane serialized on the main thread. Give every XCTest-bound command a deadline, and bound AX calls with the AXTimeout/_XCTSetApplicationStateTimeout scoped wrappers.
- DIFFERENT (security): bind the device listener to 127.0.0.1 only (Network.framework nw_parameters_set_local_endpoint) and reach it through USB usbmux forwarding. Require a per-run random bearer token, send no CORS headers, allow no state-changing GETs, and have no MJPEG port. This is the opposite of WDA's all-interfaces, unauthenticated, CORS * default.
- DIFFERENT (timing): execute choreography on device. Resolve targets (snapshot or OCR) during the previous hold, then inject with a single XCSynthesizedEventRecord per gesture (XCPointerEventPath initForTouchAtPoint:offset: / moveToPoint:atOffset: / liftUpAtOffset:) through XCUIDevice.eventSynthesizer. This path has no quiescence wait and gives arbitrary paths such as pull-to-refresh, Focus swipes and the Control Center drag. Log mach_continuous_time at submit and at completion.
- DIFFERENT (quiescence): turn XCTest quiescence off by default for the target app. Primary: wrap public element actions in -[XCUIApplication _performWithInteractionOptions:(SkipPre|SkipPost = 0b11) block:]. Fallback: WDA-style swizzle of -[XCUIApplicationProcess waitForQuiescenceIncludingAnimationsIdle:isPreEvent:], the only variant on Xcode 26.6. Never add a forced post-gesture stability wait (WDA's animationCoolOffTimeout). Replace idle waits with explicit 'wait for element/screen' polling (e.g. every 100 ms with a timeout).
- COPY with limits: use public XCUIApplication.snapshot() as the accessibility source (label, identifier, elementType, frame, value, enabled). Compute visibility as frame ∩ screen. Add the private maxDepth injection (XCAXClient_iOS defaultParameters) only if the snapshot-latency spike demands it. Use Vision OCR on XCUIScreen.main.screenshot() for text without AX nodes (e.g. 'shepherd' in the Word lens).
- Use public APIs wherever they exist: XCUIApplication(bundleIdentifier:) launch/activate/terminate/state; XCUIDevice.shared.press(.home); SpringBoard icons via XCUIApplication(bundleIdentifier: "com.apple.springboard"); XCUIDevice.shared.system.open(_:) or XCUIApplication.open(_:) for URLs (iOS 16.4+); XCUIScreen.main.screenshot(); XCUIDevice.orientation; typeText for non-secret text. Isolate private calls in one module (PrivateXCT) that runs a capability probe at start-up.
- Lock screen: use private -[XCUIDevice pressLockButton] (on Xcode 26.6 it is an XCDeviceEvent 0x0C/0x30 Power press) with a direct XCDeviceEvent performDeviceEvent:error: fallback. Read lock state through notify_register_dispatch("com.apple.springboard.lockstate"). Unlock is always a human checkpoint, detected by lockstate plus the screen; the runner may perform the post-Face-ID swipe if the spike allows. This needs the owner's acceptance of private API (❓).
- Checkpoint detection: copy WDA's 'who owns this pixel' technique (daemon _XCT_requestElementAtPoint:reply:) and/or XCUIApplication.state for known bundle ids (SpringBoard, the target, the system sheet hosting Sign in with Apple) to detect when the human finished; poll with a timeout and play the Mac alert.
- Launch and lifecycle: do not use devicectl process launch on iOS 26 (WDA#1147, xcuitest#2985). Launch with xcodebuild test-without-building -xctestrun, supervised by the Mac CLI, with automatic restart and a pre-take passcode checkpoint. A separate host app is optional (WDA uses USES_XCTRUNNER=YES with no TEST_TARGET_NAME). Keep the runner icon off the home-screen page shown in scene 1.
- Freeze the toolchain during production: Xcode 26.6 + iOS 26.3, with auto-update off on both. WDA's history shows each major iOS/Xcode version breaks something private (pressLockButton, typing, header layout).
- Licence: write Contrarregra in Swift from scratch, copying techniques, not text. If any WDA snippet is ported, keep the BSD-3 header in that file and add THIRD_PARTY_NOTICES.md with the full WDA LICENSE text. Never vendor WDA's PrivateHeaders (Apple SDK dumps) or the Apache-2.0 LRUCache; declare minimal @objc protocols or selectors yourself; never imply endorsement by Facebook/Meta or Appium.
- Why build instead of reusing WDA: WDA is a request/response WebDriver server. Contrarregra needs (1) on-device choreography with ms-level scheduling that survives network loss; (2) pause/resume human checkpoints with auto-detection; (3) a timestamped narration log aligned to the OBS timeline; (4) an MCP-first command surface; (5) a secure, loopback-only, authenticated transport; (6) no forced 2 s stability waits and no quiescence coupling with a continuously animating app. Most of WDA's ~20k lines (W3C protocol, XPath/class-chain, tvOS/watchOS, MJPEG, Appium settings) are unneeded surface area.
- What we lose by not reusing WDA, stated honestly: ten years of edge-case fixes, plus fast community fixes for each new iOS/Xcode version (e.g. iOS 27 lock fixed in weeks); ready selectors (XPath, class chain, predicates); alert heuristics; keyboard quirks; Appium Inspector and mobile-mcp compatibility; prebuilt packaging; other people's launch tooling (go-ios, pymobiledevice3, Appium RemoteXPC). Mitigation: keep stock WDA (or WDA plus a custom FBCommandHandler class, which auto-registers) as a debug/exploration fallback and a reference implementation to diff against when a private API breaks.

### F8 [verified] HTTP server: WDA's own minimal HTTP/1.1 server on Network.framework (FBHTTPServer + FBTCPSocket), not RoutingHTTPServer/CocoaHTTPServer/GCDWebServer
Introduced in v16.7.0 (2026-08-22, #1221, 'unify HTTP server across iOS/tvOS/watchOS on Network.framework'). FBTCPSocket uses nw_parameters_create_secure_tcp(NW_PARAMETERS_DISABLE_PROTOCOL…), nw_listener_create_with_port (or nw_listener_create plus nw_parameters_set_local_endpoint when an interface is set) and nw_connection_receive/send. ### F29 [likely] On iOS 15+ real devices XCTest automation needs passcode authentication at session start and shows an 'Automation Running — Hold both volume buttons to stop' overlay
Appium troubleshooting docs: real devices on iOS/iPadOS 15+ require the passcode or Touch ID when a new session starts. The overlay appears while WDA runs and is not visible in screenshots. A WDA maintainer said it is 'by design in iOS 15 for general XCTest(UI) process on real devices' and that devices without a passcode avoid the prompt. Holding both volume buttons clears the overlay, which ends automation. Settings → Developer → Enable UI Automation must be on, and users report random re-prompts over hours or days (Apple forum 740785, no answer). Not yet confirmed for iOS 26.3: whether the overlay shows in a USB (CoreMediaIO) capture, and whether human touches are blocked while automation is active.

### F30 [likely] Disabling quiescence has a known side effect: later actions no longer wait for transitions
appium#21427 (iOS 26 beta, 'Timeout waiting until the home screen is visible'): a maintainer tied the failure to quiescence being disabled for both the app and SpringBoard. appium#21469: a huge waitForIdleTimeout made WDA hang for hours on an app that keeps its UI thread busy ('Waiting up to 1728000000s until … is in idle state'). Implication for Contrarregra: replace XCTest quiescence with explicit polling for the expected element or screen, with a deadline.

### F31 [verified] WDA can be extended without forking its server: every class conforming to FBCommandHandler is registered automatically
+[FBWebServer collectCommandHandlerClasses] uses FBClassesThatConformsToProtocol(@protocol(FBCommandHandler)) and honours an optional +shouldRegisterAutomatically. Linking a class with +routes (FBRoute GET/POST … respondWithTarget:action:, .withoutSession, .standalone) into the runner adds endpoints. Session routes are prefixed /session/:sessionID. This is a realistic hybrid option: stock WDA plus a Contrarregra handler.
