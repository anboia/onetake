# transport: Starting an XCUITest runner on a real iOS 17+/iOS 26 device and reaching it over USB (Appium/WDA, go-ios, pymobiledevice3, mobile-mcp/mobilecli, plus callstack/agent-device as a TypeScript reference)

## SUMMARY
On iOS 17+ every host-managed XCUITest runner is held alive by a host-side IDE/testmanagerd session. The tools reach that session through the CoreDevice/RemoteXPC tunnel: xcodebuild, go-ios runwda and pymobiledevice3 dvt xcuitest all work this way. When that session ends, the runner exits. The device log line is "XCTestCore: Exiting due to IDE disconnection", and go-ios and pymobiledevice3 also kill the runner themselves. So killing xcodebuild, sleeping the Mac, or losing the tunnel kills the runner. The only path without a host session is Appium's "preinstalled WDA": `xcrun devicectl device process launch` of the .xctrunner with the device's own XCTest frameworks. It works for iOS 17–26 with Xcode 26, but it is broken with Xcode 27 ("Failed to background test runner", appium#22636). It is also unproven whether that runner survives losing the host connection. For app traffic, usbmuxd Connect (iproxy, go-ios forward, pymobiledevice3 usbmux forward, appium-ios-device) still works on iOS 17–26 for any device TCP port. It reaches listeners bound only to 127.0.0.1: devicekit-ios binds 127.0.0.1:12004 and mobilecli reaches it only through usbmux. It needs no root and no tunnel, and on macOS 26 usbmuxd lists the phone only while it is cabled (ConnectionType USB), so this path is USB-only by construction. The CoreDevice tunnel IPv6 address (devicectl tunnelIPAddress, kernel-routable through remoted, no root) also works, but it is held up on demand, often runs over Wi-Fi, pays a re-probe cost after idle (agent-device measured 4.5 s), and may hit Local Network privacy rules. The biggest risk for scene 9: Apple DTS says CoreDevice keeps a Wi-Fi tunnel even after the cable is plugged in, and this iPhone is currently transportType=localNetwork. Airplane Mode turns off all radios except Bluetooth (per Apple support), so on Wi-Fi the IDE session and the runner would die. Apple DTS did show USB debugging continuing with Airplane Mode on, so a wired tunnel probably survives, but this must be measured. Third-party tunnels are fragile on iOS 26: go-ios's userspace tunnel breaks on iOS 26.5 (#772), and pymobiledevice3's RSD clashes with remoted on iOS 26.2+ (#1994) can make Xcode/devicectl lose the device. Contrarregra should therefore use Apple's own tooling to start the runner (xcodebuild test-without-building), its own usbmux client in Node for the command channel (runner bound to loopback), and a preflight check that devicectl reports transportType=="wired". The design should tolerate disconnection: the choreography runs on the device and the Mac reconnects afterwards. A devicectl-launched runner is the plan B if the xcodebuild session does not survive Airplane Mode.

## RISKS
- [blocker] The runner is killed when scene 9 turns on Airplane Mode, because the xcodebuild/testmanagerd 'IDE' session drops.
  why: The runner's life depends on the host IDE session ('Exiting due to IDE disconnection'). The Appium maintainer names Airplane Mode as a cause. This phone currently reports transportType=localNetwork, and on Wi-Fi the loss is certain. Over a wired tunnel it is only likely to survive, based on Apple DTS's debugger test, not an XCTest test.
  spike: S0-AIR. Bring the tunnel to wired and verify with `devicectl list devices --json-output` (transportType=='wired', tunnelState=='connected'). Start the runner with xcodebuild test-without-building. Ping it over usbmux at 10 Hz with a persistent socket, while also streaming `log stream`/idevicesyslog filtered for XCTestCore. Turn Airplane Mode on (Control Center by hand, then by the runner via XCUITest), hold 60 s, turn it off. Record: runner PID before and after (`devicectl device info processes --filter`), whether xcodebuild is still alive, longest ping gap, socket resets, and any 'Exiting due to IDE disconnection'. Repeat 10 times, then once more deliberately on localNetwork as the negative control.
  success: 10/10 trials on wired: same runner PID, xcodebuild still running, no IDE-disconnection log, usbmux control socket either never resets or reconnects within 2 s, and the longest ping gap is 2 s or less. The localNetwork control reproduces the runner death, which proves the wired gate is needed.
  planB: (1) Launch the runner with `xcrun devicectl device process launch --terminate-existing --environment-variables … <runner>.xctrunner` (runner .app without Frameworks/XC*, Xcode 26.6 pinned) so no IDE session exists, then rerun S0-AIR. (2) If that also fails, run scene 9 fully on the device: buffer events in memory and in the app container, have the Mac reconnect after Airplane Mode is off, and pull the log with `devicectl device copy from`. (3) Last resort: a human toggles Airplane Mode while the runner pauses at a checkpoint; if the runner dies, restart it before scene 10, at the cost of a visible pause.
- [high] The CoreDevice tunnel stays on Wi-Fi with the cable plugged in, so the take's session is not actually USB.
  why: Apple DTS: CoreDevice keeps using Wi-Fi after the wire is connected. The device reports localNetwork today. Turning off the Mac's Wi-Fi (TN3158) would also cut Claude Code and the network the app needs.
  spike: S0-WIRED. Plug the cable. Poll devicectl JSON every 1 s for 120 s. If still localNetwork, turn off the iPhone's Wi-Fi in Settings (not Control Center) for 10 s and then back on; separately try turning the Mac's Wi-Fi off for 10 s. Measure time until transportType=='wired', then whether it stays wired for 30 min with both Wi-Fi radios on. Also confirm usbmuxd ListDevices shows ConnectionType 'USB' for the UDID.
  success: Wired reached within 30 s using one documented procedure, and still wired after 30 min with Wi-Fi back on (0 flips back to localNetwork). Preflight can then check this automatically.
  planB: Keep the iPhone's Wi-Fi off during the whole take and use cellular for the app's online scenes, if the phone has a SIM and the owner accepts it. Otherwise only start a take after the forced-wired dance and re-check transportType right before scene 9. Last resort: the plan B of the airplane-mode risk (devicectl launch plus on-device autonomy).
- [high] Locking the screen in scene 3, or Auto-Lock, kills or wedges the runner, or blocks app launch/AX capture until a human unlocks.
  why: agent-device reported that the runner died mid-series unless Auto-Lock was Never, and that a locked phone blocks launches ('Locked' denial). The Appium maintainer cites locking as a cause of IDE disconnection. WDA's lock commands suggest the runner itself survives a lock.
  spike: S0-LOCK. With the runner up over usbmux, lock via the runner (XCUIDevice pressLockButton) and via the side button. Hold 10 s, 60 s and 5 min. While locked, call /health and take a SpringBoard snapshot and a screenshot. Have a human unlock with Face ID, then let the runner wait for Hagah's screen. Record the runner PID, usbmux socket state, and latency until the first successful app snapshot after unlock.
  success: 5/5 locks of 60 s or less survive with the same PID, /health answers while locked, and the first good app snapshot comes 1.5 s or less after unlock. A 5 min lock survives in at least 4/5.
  planB: Set Auto-Lock to Never in preflight and keep the scene-3 lock short. If the runner dies, the supervisor restarts xcodebuild once the phone is unlocked (warm restart about 5 s per agent-device) and resumes the choreography from the scene-3 checkpoint, which is already a human checkpoint.
- [medium] The Mac-side xcodebuild process dies (Mac sleep, terminal closed, SIGPIPE, the supervisor restarting) and takes the runner with it.
  why: The runner exits when the IDE session goes away. agent-device found that pipe-based stdio killed runners with SIGPIPE after their parent daemon exited.
  spike: S0-SOAK. Spawn xcodebuild detached with stdio to a log file, under `caffeinate -dimsu`. Leave the runner idle for 2 h, then run 30 min of mixed commands (snapshots, taps, screenshots). Restart the MCP server/CLI in between and confirm it re-attaches to the same runner.
  success: 0 runner restarts in 2.5 h, re-attach after an MCP restart in 2 s or less, and the runner's RSS growth stays under 100 MB.
  planB: The supervisor detects a dead xcodebuild through its exit event and a /health failure, restarts it (target: 10 s warm, 60 s cold), and the choreography resumes from the last completed step or checkpoint.
- [medium] Command-channel latency or jitter over usbmux is too high for interactive exploration or for ±100 ms clock sync.
  why: No published round-trip numbers for usbmux on iOS 26. agent-device saw 440 ms per snapshot, dominated by AX work, and opens a fresh usbmux handshake per command.
  spike: S0-RTT. From Node, open /var/run/usbmuxd, Listen, pick the device with SerialNumber==UDID and ConnectionType=='USB', Connect to the runner port. Send 1000 64-byte echo requests and 100 64 KB echoes on one persistent connection, then 1000 using a new connection per request. Take 100 screenshots (JPEG q75, full resolution) and 50 accessibility snapshots of Hagah. Estimate the clock offset Mac to device with an NTP-style exchange, keeping the 10% lowest-RTT samples. Repeat with Airplane Mode on.
  success: Persistent echo p50 5 ms or less and p95 20 ms or less; new-connection p95 50 ms or less; screenshot p95 400 ms or less; standard deviation of the offset estimate 5 ms or less (well within ±100 ms); no change with Airplane Mode on.
  planB: Run the runner on the CoreDevice tunnel IPv6 address as well (warm probe measured at 6–8 ms by agent-device), only while the tunnel is wired. For the take itself rely on on-device timestamps, which do not depend on the channel's round trip.
- [medium] Third-party tunnel tools (go-ios, pymobiledevice3 kernel or --native tunnels) break on iOS 26.x or disturb Xcode's own connection.
  why: go-ios #772: the userspace tunnel drops on iOS 26.5 and the maintainers can't test above iOS 18. pymobiledevice3 #1994: on iOS 26.2+ the device keeps a single RSD peer, and remoted can stop redialing, so devicectl/Xcode lose the phone until replug. The phone runs iOS 26.3.
  spike: None needed if Contrarregra uses only Apple tooling (xcodebuild/devicectl) plus raw usbmux. If a diagnostic tool is ever needed, test pymobiledevice3's default userspace mode once, and run `devicectl list devices` after it to confirm the device is still tunnelState connected.
  success: The production path has no dependency on go-ios or pymobiledevice3; preflight never sees remoted 'Heartbeat failed'.
  planB: If xcodebuild cannot start the runner, try pymobiledevice3 `developer dvt xcuitest` in its default no-root userspace mode as a diagnostic or launcher. Do not use --native or sudo tunnels.
- [medium] Upgrading Xcode (e.g. to Xcode 27 and its DDI) changes XCTest behaviour mid-project.
  why: With the Xcode 27 DDI stack, devicectl-launched runners can't background themselves, even on iOS 26.5.2 (appium#22636). On iOS 27, pressLockButton no longer locks (WDA source).
  spike: None now. Preflight records `xcodebuild -version`, the devicectl version, the iOS build and the DDI state, and refuses to take when they differ from the validated set (Xcode 26.6 17F113 / iOS 26.3 23D127).
  success: The take only runs on the validated toolchain; any change forces S0-AIR, S0-LOCK and S0-RTT to be re-run.
  planB: Keep Xcode 26.6 side by side (DEVELOPER_DIR) for takes. The xcodebuild bootstrap path is the most robust across versions.
- [medium] The runner's icon (and a host app's icon, if one exists) shows on the Home Screen or in App Library during scene 1.
  why: An xctrunner is installed as a normal app with an icon (WDA even ships one). The hard requirement is that nothing of the tool appears in the recording.
  spike: S0-ICON. Install the runner with no host app (UI test bundle without TEST_TARGET_NAME, as WDA does). Check where icons appear. Use 'Remove from Home Screen' to send it to App Library only, then confirm xcodebuild test-without-building still launches it and that scene 1's Home Screen page shows nothing of the tool.
  success: Scene-1 frames contain no Contrarregra icon or label, and the runner still starts after its icon has been removed from the Home Screen.
  planB: Put the icon on the last Home Screen page or inside a folder that scene 1 never shows, and give the runner a neutral display name. This becomes a preflight human checkpoint.
- [low] An 'Untrusted Developer', 'Allow accessory to connect' (iOS 26 Wired Accessories) or 'Trust This Computer' prompt blocks the first launch or the USB data link.
  why: Apple DTS says trust isn't needed for paid-team development builds, but iOS 26 added prompts for wired accessories, and the cable may never have been used with this Mac and phone pair, since installs so far were over the network.
  spike: S0-PROMPTS. Plug the cable with the phone unlocked and note every prompt. Launch the runner for the first time and note any trust or Developer Mode dialogs. Check Settings > Privacy & Security > Wired Accessories.
  success: After a one-time preflight (Allow, or setting 'Automatically Allow When Unlocked'), replugging and launching show no prompts in 3/3 tries.
  planB: Document a human preflight step: trust under Settings > General > VPN & Device Management, set Wired Accessories, and accept Trust This Computer.
- [medium] Pulling the runner's event log after the take with `devicectl device copy from --domain-type appDataContainer` does not work for an .xctrunner bundle.
  why: Appium pulls XCTest attachments from the special com.apple.testmanagerd container. Whether an xctrunner's own data container is exposed has not been verified.
  spike: S0-PULL. The runner writes Documents/contrarregra/events.jsonl (1 MB). Run `xcrun devicectl device info files --device <udid> --domain-type appDataContainer --domain-identifier <runner>.xctrunner`, then `… device copy from … --source Documents/contrarregra/events.jsonl --destination ./events.jsonl`, both with the runner running and after it has stopped.
  success: The file is copied byte-identical in 5 s or less in both states.
  planB: Stream events over the usbmux channel and replay any buffered backlog after reconnect. As a fallback, expose GET /events?since=<seq> from the runner.
- [low] An MCP server spawned by the Claude desktop app is blocked by macOS Local Network privacy if it uses tunnel IPv6 or LAN addresses.
  why: TN3179 automatically allows only Terminal/SSH children, launchd daemons and root. Other responsible apps need the permission.
  spike: Only if the tunnel-IP fallback is used: from the MCP process launched by the Claude desktop app, open TCP to [tunnelIPAddress]:port and watch for EHOSTUNREACH or a prompt.
  success: The usbmux path works from both a Terminal-launched and a desktop-launched MCP server with no prompt.
  planB: Use usbmux only (a unix socket is not covered by local-network privacy), or run the device daemon as a launchd agent with AssociatedBundleIdentifiers set.

## RECOMMENDATIONS
- Bootstrap with Apple tooling only. Build once per runner change with `xcodebuild build-for-testing -project Contrarregra.xcodeproj -scheme Runner -destination 'generic/platform=iOS' -allowProvisioningUpdates DEVELOPMENT_TEAM=984PNJZ8B9 CODE_SIGN_STYLE=Automatic`. Start each session with `xcodebuild test-without-building -xctestrun <session>.xctestrun -destination id=00008101-001E79203A68001E -only-testing Runner/RunnerTests/testServe -test-timeouts-enabled NO -collect-test-diagnostics never -parallel-testing-enabled NO -destination-timeout 60`. Spawn it detached, send stdout/stderr to an append-mode log file (never pipes), and run it under `caffeinate -dimsu`. Put configuration in the per-session .xctestrun EnvironmentVariables or TEST_RUNNER_* variables. Consider UseDestinationArtifacts so a take does not reinstall anything.
- Make the runner a UI test bundle with no host app, like WDA, so only one .xctrunner is installed and only one icon needs hiding. It should run one never-ending test (XCTWaiter with a 24 h timeout or a run loop), bind its server to 127.0.0.1 only on a fixed port, and log 'CONTRARREGRA_READY port=N' when it is listening.
- Command channel: write a small Node usbmux client, with no external binary. It connects to /var/run/usbmuxd and sends Listen to get attach/detach events. On ListDevices it picks Properties.SerialNumber == UDID AND ConnectionType == 'USB', then sends Connect{DeviceID, PortNumber: htons(port)}. Keep one persistent framed connection (WebSocket or newline-delimited JSON) with a 1 Hz heartbeat, and reconnect with exponential backoff capped at 2 s. Fail fast with 'connect the cable' when usbmuxd doesn't list the device. agent-device's TypeScript is MIT and can serve as a reference. No sudo, no third-party tunnel, no Local Network permission needed.
- Add a preflight gate that refuses to record unless all of these hold: devicectl JSON shows transportType=='wired', tunnelState=='connected', ddiServicesAvailable==true and developerModeStatus=='enabled'; usbmuxd lists the UDID as USB; runner /health answers within 2 s; Auto-Lock is Never; Wired Accessories is allowed; the toolchain matches the validated set (Xcode 26.6 17F113, iOS 26.3 23D127). If transportType is localNetwork, guide the owner through the forced-wired procedure (iPhone Wi-Fi off in Settings for 10 s, then on) and check again.
- Design for losing the connection rather than assuming it survives. The choreography is uploaded whole and runs on the device. Every event carries a monotonic timestamp and is buffered in memory and in Documents/ inside the runner container. The Mac re-attaches and fetches events by sequence number after any drop. Re-run clock sync (NTP-style, keeping the minimum-RTT samples) after every reconnect.
- Keep a plan-B bootstrap ready but disabled: `xcrun devicectl device process launch --device <udid> --terminate-existing --environment-variables '{"CONTRARREGRA_PORT":"<n>"}' <runner>.xctrunner` with a runner .app stripped of Frameworks/XC*. It has no host IDE session, so it may survive tunnel loss. It only works with Xcode 26.x (not 27). Turn it on only if S0-AIR fails on the xcodebuild path.
- Do not depend on go-ios or pymobiledevice3 at runtime: iOS 26.5 tunnel breakage (#772), remoted contention on iOS 26.2+ (#1994), and pymobiledevice3 is GPL-3. mobilecli and devicekit-ios are FSL-1.1, so copy techniques only. WDA (BSD-3) and agent-device (MIT) are safe sources of code ideas.
- Optionally also bind the runner to the CoreDevice tunnelIPAddress (read from devicectl JSON), but only for debugging and only when the tunnel is wired. Never bind 0.0.0.0 or the Wi-Fi address: the server is unauthenticated, and devicekit warns against exactly this.
- MCP tool design, borrowed from mobile-mcp: element refs ('@e5') valid until the screen changes; one compact line per element (type, label, identifier, frame, non-default states); screenshots downscaled to JPEG with an explicit pixel-to-point note; a batch tool with stopOnError; readOnly/destructive annotations; server instructions that steer the agent toward refs. Contrarregra-specific additions: record_step (turn the last action into a choreography step), transport_status (wired/usbmux/runner PID) and checkpoint_wait.
- Run the phase-0 spikes in this order: S0-WIRED, S0-RTT, S0-AIR (blocker), S0-LOCK, S0-SOAK, S0-PULL, S0-ICON, S0-PROMPTS. Use agent-device's numbers as baselines: warm re-adopt 1.15 s, runner self-heal 4–5 s, cold start 20–38 s, warm probe 6–8 ms.

## FINDINGS
### F1 [verified] Appium's default real-device bootstrap is xcodebuild build-for-testing + test-without-building (or test-without-building alone with -xctestrun when useXctestrunFile/usePrebuiltWDA), always with -destination id=<UDID>; quitting sends SIGTERM to xcodebuild, then SIGKILL after 1 s.
Args are built in getCommand(): ['build-for-testing','test-without-building'] or ['test-without-building'], '-xctestrun <file>' or '-project … -scheme WebDriverAgentRunner [-derivedDataPath]', '-destination id=<udid>', IPHONEOS_DEPLOYMENT_TARGET=<maj.min>, DEVELOPMENT_TEAM/CODE_SIGN_IDENTITY, PRODUCT_BUNDLE_IDENTIFIER=<updatedWDABundleId>, GCC_TREAT_WARNINGS_AS_ERRORS=0, COMPILER_INDEX_STORE_ENABLE=NO, -allowProvisioningUpdates -allowProvisioningDeviceRegistration. Status is polled every 0.5 s until wdaLaunchTimeout (default 60 s). Implication: Contrarregra can copy this exactly, with team 984PNJZ8B9 and automatic signing.

### F2 [verified] xcodebuild does NOT pass its own environment to the test runner. Only TEST_RUNNER_<VAR> variables are passed (with the prefix removed), or EnvironmentVariables/TestingEnvironmentVariables set in the .xctestrun file (FormatVersion 2).
From the man page of the installed Xcode 26.6 (17F113): 'TEST_RUNNER_Foo=Bar xcodebuild test … sets Foo=Bar in the test runner's environment'. WDA writes USE_PORT into the xctestrun's EnvironmentVariables (lib/utils/xctestrun.ts:60-75). agent-device writes its port into a per-session xctestrun EnvironmentVariables entry because 'only names prefixed TEST_RUNNER_ cross that boundary'. For Contrarregra: put CONTRARREGRA_PORT, CONTRARREGRA_SESSION_ID, etc. in a per-session .xctestrun or in TEST_RUNNER_* variables.

### F3 [verified] In an .xctestrun file, UseDestinationArtifacts plus TestHostBundleIdentifier, TestBundleDestinationRelativePath and UITargetAppBundleIdentifier make xcodebuild use artifacts already installed on the device and skip reinstalling.
Per man 5 xcodebuild.xctestrun (Xcode 26.6), when UseDestinationArtifacts is set, TestBundlePath, TestHostPath and UITargetAppPath must be omitted, and the bundle-identifier keys are mandatory. This lets a take start without reinstalling the runner. UITargetAppBundleIdentifier could also name app.kifactory.hagah (the TestFlight build) without needing its .app. XCUIApplication(bundleIdentifier:) at runtime is the simpler option.

### F4 [verified] The established way to keep a runner alive: one never-ending test, launched with specific xcodebuild flags, with xcodebuild spawned detached and its stdio sent to a file.
Never-ending test: WDA's UITestingUITests.testRunner calls FBWebServer startServing; agent-device uses XCTWaiter.wait(timeout: 24*60*60). agent-device launch: `xcodebuild test-without-building -only-testing AgentDeviceRunnerUITests/RunnerTests/testCommand -parallel-testing-enabled NO -test-timeouts-enabled NO -collect-test-diagnostics never -maximum-concurrent-test-device-destinations 1 -destination-timeout N -xctestrun <session>.xctestrun -derivedDataPath <dir> -destination id=<udid>`, spawned detached with stdio sent to an append-mode file rather than pipes. Pipes caused SIGPIPE deaths of runners after their parent daemon exited (#2681). devicekit's README also recommends -collect-test-diagnostics never, because a failed start otherwise stalls xcodebuild for minutes collecting a sysdiagnose. All of these flags exist in the local Xcode 26.6 man page (-destination-timeout defaults to 30 s).

### F5 [verified] The runner's life is tied to the host IDE/testmanagerd session. When that session drops (xcodebuild killed, host process exits, tunnel lost), iOS terminates the runner.

Implication: the xcodebuild process must stay alive for the whole session (supervisor, caffeinate), and any loss of the tunnel can kill the runner mid-take.

### F7 [verified] Preinstalled-runner path with no xcodebuild (Appium usePreinstalledWDA, iOS 17+): the xctrunner is launched by RemoteXPC process control, or on macOS by falling back to `xcrun devicectl device process launch`. This path has no host IDE session.
RemoteXPC call: dvt.processControl.launch({bundleId, environment, killExisting:true, extraOptions:{ActivateSuspended:true}}). Fallback command: `xcrun devicectl device process launch --device <udid> --terminate-existing --environment-variables '{"USE_PORT":"8100","WDA_PRODUCT_BUNDLE_IDENTIFIER":"<id>.xctrunner"}' <id>.xctrunner` (the bundle id must be the last argument). Requirements: remove Frameworks/XC*.framework from the runner .app so it loads the device's XCTest from the DDI (WDA PR #868, v7.3.0), and the DDI must be mounted. A devicectl-launched runner starts in the foreground and must press Home to background itself. Under Xcode 27's DDI stack that press is ignored, giving 'Failed to background test runner within 30.0s … Code=10300' even on iOS 26.5.2, so Appium disables this fallback on iOS 27+. Plain host (Xcode 26.6) is not affected. Implication: this is a plan B whose runner is independent of xcodebuild, valid only while Xcode stays at 26.x.
SRC: appium/appium-xcuitest-driver@80b1ac3f:lib/device/wda-host-ops.ts:160-245 ; appium/node-devicectl@e5f2b709:lib/mixins/process.ts ; appium-xcuitest-driver docs/guides/run-preinstalled-wda.md ; https://github.com/appium/WebDriverAgent/pull/868 ; https://github.com/appium/appium/issues/22636

### F8 [verified] devicectl 518.33 (Xcode 26.6) offers the subcommands needed here, and its only supported machine interface is --json-output <file>.
Process launch: `devicectl device process launch --device <id> [--terminate-existing] [--environment-variables JSON] [--activate|--no-activate] [--start-stopped] [--console] <bundle-id-or-path> [args]`. Environment variables can also be passed as DEVICECTL_CHILD_<VAR>. Other commands: `device process terminate --pid N [--kill]`; `device process signal`; `device info processes --filter <NSPredicate>`; `device info apps [--bundle-id X] [--include-all-apps]`; `device install app <path>`; `device uninstall app <bundleId>`; `device info details`; `device info files --domain-type appDataContainer --domain-identifier <bundleId> [--subdirectory]`; and to pull a log after the take, `device copy from --domain-type appDataContainer --domain-identifier <runner>.xctrunner --source <path> --destination <path>`. Valid domains: temporary, appDataContainer, appGroupDataContainer, systemCrashLogs. `manage ddis` manages host DDIs. There is no `device capture screenshot` in 518.33. The help text states that 'JSON output to a user-provided file on disk is the ONLY supported interface'.
SRC: local `xcrun devicectl <subcommand> --help` (devicectl 518.33, Xcode 26.6 17F113)
